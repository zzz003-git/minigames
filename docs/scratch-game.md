# ⑳ 슥슥 긁기 — 구현 명세

기획서 `../reward-minigame-research/plans/2026-07-30/PLAN-14_슥슥긁기.md`
(`IDEA-2026-0014`, 안정형 / 엔진 F 랜덤 결과)를 이 저장소로 구현한 문서입니다.

두 가지가 앞의 19종과 다릅니다.

1. **조작이 탭이 아닙니다** — 문지르기(포인터 궤적). 아케이드 규격을 벗어난 항목이라 §5 에 이유를 적었습니다.
2. **결과가 순수 난수입니다** — 실력·판단·기억이 점수를 바꾸지 않는 첫 게임입니다.

---

## 1. 왜 이 게임인가 (기획서 2장 요약)

기획서의 출발점은 데이터가 아니라 **원리**입니다.

- **원리 8 규칙 안의 서프라이즈** — 무엇이 나올지 모르는 카드. 단 서프라이즈가 규칙
  (심볼 6종 · 매칭 3개) 안에서 일어나 예측 가능성과 놀라움이 함께 있습니다.
- **원리 2 손맛** — 문지르면 은박이 밀려나며 그림이 드러나는 촉감. 복권 긁기는 전 국민이
  이미 아는 쾌감이라 설명이 필요 없습니다(기획서 0-2 「글 없음」).

자사 배포분 19종에 **순수 F(랜덤 결과)형이 한 종도 없었습니다.** 조사된 시장 F형 11종
(행운상자 · 사다리 · 룰렛 · 보물상자)은 전부 **1터치 후 결과 통보**여서 조작의 손맛도
어디를 여는지의 선택권도 없습니다.

## 2. 게임 규칙 (구현값)

| 항목 | 값 | 근거 |
|---|---|---|
| 진행 방식 | `ENDLESS` | 칸 하나를 긁을 때마다 서버가 판정 |
| 분류 | **puzzle** | 반응속도 완전 비의존 — §7 |
| 카드 | 3×3 **9칸** | 기획서 4장 |
| 한 판 | **5번** 긁기 (광고로 +1) | 기획서 4장 |
| 기본 도전 기회 | 하루 **카드 1장** | 기획서 6장 |
| 카드 추가 광고 | **없음** (`adAttemptsPerDay: 0`) | 기획서 8장 — 광고는 「한 칸 더」 하나뿐 |
| 런 중 이어하기 | **1회** = 한 칸 더 긁기 | 기획서 8장 구원 광고 |
| 목숨 | `1` — **남은 긁기의 표현**이지 실패가 아님 | §4 |
| 심볼 | **6종** (커피·도넛·음료·아이스크림·버거·치킨) | 기획서 4장 · 10장(광고 지면) |
| 매칭 | 같은 그림 **3개** → 획득분 **2배** | 기획서 4장 |
| 힌트 | 일반 2칸 / 첫 주 3칸 — **색만** 비침 | 기획서 4장 + §5 |
| 힌트 강화 | 연속 **7일**째 카드는 심볼 1개 완전 공개 | 기획서 4장 6번 |
| 연속 보너스 | 연속 7일마다 **+50P** | 기획서 7장 |
| 제한 시간 | **없음** | 반응속도 비의존이 전제 — 시간 초과로 못 긁은 칸이 생기면 「꽝 없음」이 깨집니다 |

수치는 전부 `src/lib/config.js` 의 `ARCADE.SCRATCH` 에 있습니다.

### 한 판의 흐름

```
[ready]  최장 연속 · 오늘 남은 카드 · ▶ 카드 긁기         (광고 카드 없음)
[play]   9칸 은박 · 문질러 긁기 ×5                        3개 모이면 카드가 반짝
[pause]  "아, 하나만 더!"                                 [광고: 한 칸 더 긁기]
[over]   획득 포인트 · 연속 일수 · 내일 카드 예고           [광고: 전체 순위]
```

### 카드를 만드는 규칙

```
매칭 대상 심볼 1종을 4개(첫 주 5개) 심는다
나머지 칸은 다른 심볼로 채우되 어느 것도 2개를 넘지 않는다
→ 3개에 도달할 수 있는 심볼은 언제나 정확히 하나
```

**타겟 4개일 때 5칸을 무작위로 골라 매칭할 확률은 31.7%**
(`C(4,3)·C(5,2)/C(9,5)`), 첫 주의 5개는 47.6% 입니다. 힌트를 읽고 고르면 이보다
확실히 올라가고, 그 차이가 이 게임에서 사용자가 가진 유일한 재량입니다.

3개에 도달할 수 있는 심볼을 하나로 고정하는 이유는 「무엇을 노려야 하는가」를 흐리지
않기 위해서입니다. 우연히 다른 그림도 3개가 되면 힌트를 읽는 일이 뜻을 잃습니다.
이 규칙은 카드 200장을 뽑아 `npm run test:api` 가 매번 확인합니다.

## 3. 영속 상태 — 연속 긁기 일수

`user_progress` 는 `best_level` `best_score` `play_count` 세 값이 전부라 **마지막으로
긁은 날짜**를 담을 수 없습니다. 날짜가 없으면 "어제 긁었는가" 를 판정할 수 없고,
그러면 연속이라는 개념 자체가 성립하지 않습니다. 그래서 표를 신설합니다
(`migrations/0010_scratch_state.sql`).

```sql
CREATE TABLE scratch_state (
  user_id    TEXT PRIMARY KEY,
  streak     INTEGER NOT NULL DEFAULT 0,  -- 연속 긁은 일수
  last_day   TEXT,                        -- 마지막으로 긁은 날 (KST 'YYYY-MM-DD')
  cards      INTEGER NOT NULL DEFAULT 0,  -- 누적 카드 수 (첫 주 완화 배정의 기준)
  matches    INTEGER NOT NULL DEFAULT 0,  -- 누적 매칭 완성 수
  updated_at INTEGER NOT NULL
);
```

**카드 내용(9칸의 심볼)은 여기 저장하지 않습니다.** 그건 그 판의 정답이라 세션에
암호화해 두고 판이 끝나면 사라집니다.

### 읽고 쓰는 시점

⑲ 내 가게 채우기와 같은 훅 두 개를 씁니다.

| 훅 | 시점 | 하는 일 |
|---|---|---|
| `initSecret` | 런 시작 | 연속 일수를 읽고 오늘 카드를 배정 (`cells` 는 secret 으로) |
| `onRunEnd` | 결과 저장 직후 | 연속 일수 · 누적 카드 · 누적 매칭을 한 번 쓴다 |

라운드마다 쓰지 않는 것은 왕복 비용 때문입니다(⑮·⑲ 와 같은 선택). 대신 **판을 끝내지
않고 이탈하면 그 날은 연속에 세지 않습니다** — 세션은 1시간이면 만료되고, 하루 1판
게임이라 그날 카드도 함께 잃습니다. ⑲ 와 같은 성질이고, 하루 1판 게임의 알려진 한계로
남겨 둡니다(고치려면 시작 시점에 날짜를 먼저 찍어야 하는데, 그러면 한 칸도 긁지 않은
날이 연속으로 세집니다).

### 연속 판정

```
last_day == 오늘    → 그대로 (같은 날 두 번째 판이 연속을 두 번 세지 않도록)
last_day == 어제    → +1
그 밖 · 첫 방문     → 1
```

날짜는 KST 자정 기준(`lib/time.js` 의 `dayKey`)입니다. 기획서 8장의 「내일 카드가
밤 12시에 도착해요」와 일일 기회 리셋이 같은 시각이어야 합니다.

## 4. 목숨 1 = 남은 긁기 (실패가 아닙니다)

이 게임에는 **꽝이 없습니다**(모든 칸에 포인트 · 기획서 4장). 그래서 판정이 틀리는
경우가 없고, 판이 끝나는 유일한 길은 긁기를 다 쓰는 것입니다.

그 소진을 `lives: 1` 로 표현했습니다. `lives: 0` + `endsOnDone` 으로도 끝낼 수 있지만
그렇게 하면 판이 **끝나는 순간 세션이 닫혀** 기획서 8장의 구원 광고를 붙일 자리가
없습니다(광고 보상은 열린 세션에만 적용됩니다). 엔진에는 이미 같은 모양의 흐름이 있습니다.

```
마지막 긁기 → fatal → lives 0 → 세션은 열린 채 [pause] 화면
                                   ├─ 광고 보고 한 칸 더 → lives 1 · 긁기 +1 → [play]
                                   └─ 여기서 끝내기      → /game/finish → [over]
```

그래서 `fatal` 은 **실패가 아니라 소진의 표시**입니다. 화면 어디에도 실패로 표시되는
곳이 없습니다 — `[pause]` 의 문구는 매칭 여부에 따라 「매칭 성공!」 / 「아, 하나만 더!」 /
「카드를 다 긁었어요」 셋 중 하나입니다.

**구원 광고는 매칭 2개일 때만 띄우지 않고 늘 제시합니다.** 기획서 4장 5번은 "매칭이
2개에서 멈췄으면" 이라고 적었지만, 15장 가설 1(「매칭 2개 판의 광고 선택률이 뚜렷이
높다」)을 재려면 두 경우 모두에 제시해야 비교군이 생깁니다. 대신 **문구를 나눕니다.**
그 판이 아깝게 멈춘 판이었는지는 결과의 `near_miss` 로 기록에 남습니다.

## 5. 아케이드 규격에서 벗어난 항목

규격: 1판 10~60초 · **조작은 탭 1종류** · 단일 세션 완결 · 광고 트리거 3종.

| 항목 | 규격 | 이 게임 | 이유 |
|---|---|---|---|
| 조작 | 탭 1종류 | **문지르기**(포인터 궤적) | 기획의 핵심이 원리 2 손맛입니다. 탭으로 바꾸면 「1터치 후 결과 통보」가 되어, 시장 F형과 갈라놓은 근거가 그대로 사라집니다(기획서 11장) |
| 도전 기회 | 하루 5회 | 하루 **1장** | 아침 리추얼 포지셔닝(기획서 9장). ⑲ 와 같은 값입니다 |
| `_ATTEMPT` 광고 | 하루 5회 | **0회** | 하루 1장 고정이 사행성 방어의 근거입니다(기획서 16장 위험 1). 트리거는 규칙상 생기지만 서버가 항상 거절합니다 |
| 힌트 정보 | — | 심볼이 아니라 **색** | 아래 |

### 힌트를 색으로 바꾼 이유

기획서는 "심볼 일부가 비친다" 로 적었습니다. 구현에서는 **색만** 비치게 했습니다.

심볼이 비치면 힌트 칸은 곧 정답이 되고, 힌트 칸부터 긁는 것 외에 판단할 것이 없어집니다.
색 하나에 심볼을 두 종씩 걸어 두면 「노란빛 두 칸이 커피 두 개일까, 커피와 도넛일까」가
남습니다 — 관찰이 확정이 아니라 **추론**이 됩니다. 기획서 장면의 「노란 것이 비친다」가
물리적으로도 더 맞습니다(작은 은박 조각으로 보이는 것은 색이지 모양이 아닙니다).

연속 7일째의 힌트 강화는 그래서 **의미가 있습니다** — 그 한 칸만 색이 아니라 그림이
공개됩니다.

### 문지르기의 대체 경로 (접근성)

규격이 「탭 1종류」인 뜻은 *WebView 어디서든 같게 동작할 것*입니다. 그래서 마우스·터치가
없는 경로를 함께 둡니다.

| 입력 | 한 칸을 긁는 방법 |
|---|---|
| 터치 · 마우스 | 문지르기. 은박이 45% 벗겨지면 그 칸이 확정됩니다 |
| 키보드 · 보조기기 | 칸에 포커스를 두고 **Enter/Space 4번** |

키보드 경로가 한 번에 긁히면 서버의 궤적 검사(`MIN_STROKES`)에 걸려 **마우스가 없는
사용자만 순위에서 빠집니다.** 그래서 최소 입력 수를 궤적 하한과 같은 4로 맞췄습니다.

## 6. 왕복 지연을 제스처로 흡수합니다

카드 그림은 서버에만 있어 긁는 순간에는 무엇이 나올지 알 수 없습니다. `/game/round` 는
세션 읽기 + 쓰기가 있어 약 470ms 가 바닥입니다(`lib/arcade.js` 실측 주석).

```
문지르기 시작 ──── 45% 벗겨짐 ──→ 서버 신고 ─── 응답 ──→ 남은 은박 걷어내며 확정
   (손맛)          (계속 문지름)        (약 0.5초, 문지르는 동안 지나감)      (반짝)
```

기획서 0-3 「그림이 반쯤 드러나다 마지막 문지름에 반짝하며 확정」이 그대로 지연을
덮습니다. ⑬ 카드 짝 맞추기가 「탭 즉시 뒤집고 그림만 나중에 채우는」 것과 같은 처리입니다.

벗겨진 면적은 `getImageData` 로 재지 않고 8×8 격자에 표시하며 셉니다 — 매 포인터
이동마다 픽셀을 다시 읽으면 저가 단말에서 문지르는 손맛이 그대로 무너집니다.

### 브라우저 확인에서 나온 것 (API 테스트가 잡지 못한 것들)

세 가지 모두 손이 화면에 닿아 있는 동안 벌어지는 일이라 서버 테스트로는 나오지 않습니다.

| 증상 | 원인 | 대응 |
|---|---|---|
| **탭이 통째로 멈춤** | 마지막 칸을 긁으면 즉시 [pause] 로 넘어가는데 손가락은 아직 닿아 있어 pointermove 가 몇 개 더 들어온다. 숨은 화면의 캔버스는 rect 가 0×0 → 좌표가 Infinity → 선 보간 횟수가 무한 | 좌표를 만들 수 없으면 `null` 을 돌려주고 멈춘다 + 보간 횟수 상한 |
| 누르지 않고 지나가도 긁힌다 | 캡처 중 `pointerup` 을 놓치면 `drawing` 이 남아, 그 뒤의 이동만으로 은박이 벗겨진다 | `pointermove` 에서 `e.buttons === 0` 이면 멈춘다 |
| 키보드 사용자만 이상치로 찍힌다 | Enter 를 누른 채로 두면 자동 반복이 30ms 간격으로 들어와 한 칸이 0.15초에 긁힌다 → 서버의 `MIN_SCRATCH_MS` 에 걸린다 | 눌림을 받아들이는 최소 간격 100ms |

**소진된 런을 새로고침으로 이어받는 경우**도 화면에서만 드러났습니다. 긁을 칸이 없는
플레이 화면에 갇히므로, 이어받은 라운드의 남은 긁기가 0이면 [pause] 화면을 다시 그립니다.
그 화면의 광고 카드에는 "이 판에서 몇 번 썼는지" 가 필요한데 엔진의 이어받기 응답은 그
값을 0 으로 되돌리므로, 라운드에 `boosts_used` 를 실어 보냅니다.

## 7. 분류가 puzzle 인 이유

`category` 는 `action`(정답은 보이는데 제때 해내야 함) 또는 `puzzle`(정답을 알아내야 함)
둘 중 하나입니다. 이 게임은 **반응속도·순발력에 전혀 의존하지 않습니다** — 제한 시간이
아예 없고, 주력층이 30~65세입니다(기획서 3장). action 에 넣으면 순발력 묶음에 들어가
"빨리 해야 하는 게임" 으로 읽힙니다.

엄밀히 말해 알아낼 정답이 있는 것은 아니지만, 힌트 색으로 어디를 긁을지 **고르는** 것이
이 게임의 유일한 판단이라 두 묶음 중에서는 puzzle 이 맞습니다. ⑲ 내 가게 채우기와
같은 판단입니다.

## 8. 순위 지표는 연속 긁기 일수

결과가 순수 난수인 게임에서 획득 포인트로 순위를 세우면 **운 순위표**가 됩니다.
이 게임에서 사용자가 실제로 쌓는 것은 리추얼이고, 기획서 9장(재방문 장치)과
14장(핵심 KPI)이 든 것도 연속 일수입니다.

```
rank_metric = -(오늘 판까지 반영한 연속 일수)     ← 작을수록 상위
score       = Σ(긁은 칸의 포인트) × (매칭이면 2) + 연속 7일 보너스
```

개인 최고 기록(`personalBest` = 최소 `rank_metric`)이 자연히 **최장 연속**이 되므로
`best_streak` 열을 따로 두지 않았습니다.

## 9. 광고주 적용 (기획서 10장)

**심볼이 곧 광고 지면입니다.** `config.js` 의 `SYMBOLS` 6종을 광고주 상품으로 바꾸면
됩니다 — 판정·생성 규칙은 심볼의 `key` 만 보므로 그대로 둡니다. 각 심볼에는 은박이
벗겨졌을 때 비칠 `hue` 가 필요하고, **한 색에 두 종**을 유지해야 힌트가 추론으로
남습니다(§5).

브랜드 매칭 주간(3매칭 시 실물 쿠폰 추첨)·시즌 카드 스킨은 이 표를 DB 로 옮기는
작업이 먼저입니다. ⑲ 의 `ITEMS` 와 같은 성질이라 함께 옮기는 것이 좋습니다.

## 10. 검증

`npm run test:api` 가 확인하는 것(전용 시나리오 `scratchFlow` + 결정적 검사
`scratchCardRules`).

- 긁지 않은 칸의 그림 비노출 · 힌트는 색만
- 없는 칸 · 이미 긁은 칸은 거부하되 **긁기를 소모하지 않음**
- 새로고침하면 같은 카드를 이어받고 카드를 다시 쓰지 않음
- 다섯 칸 소진 → 세션 유지 + 구원 광고 대기 → 보상은 긁기를 **한 칸만** 늘림
- 하루 한 장 초과 시작 불가 · 카드 추가 광고는 항상 거절
- (결정적) 카드 200장의 구성 규칙 · 힌트 색의 정직성 · 매칭 2배 · 궤적 이상치 · 연속 판정

검사합니다 — ⑲ 의 `storeShelfRules` 와 같은 이유입니다.
