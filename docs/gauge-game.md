# ㉗ 오늘의 전국 게이지 — 구현 명세

기획서 `../reward-minigame-research/plans/2026-07-30/PLAN-17_오늘의전국게이지.md`
(`IDEA-2026-0017`, 실험형)를 구현한 문서입니다.

**이 기획서는 게임 기획서가 아닙니다.** 본문이 「독립 게임이 아니라 배포 전체를 묶는
시즌 레이어」로 못 박고 킬 테스트 대상도 아니라고 적어 두었습니다. 그래서 구현 순서를
나눴습니다.

---

## 1. 왜 게임 화면으로 먼저 넣는가

레이어로 얹으려면 **전역 카운터·해금 판정·정산**이 실제로 도는지 먼저 확인해야 합니다.
그 셋을 확인할 가장 작은 형태가 「게이지를 보고 직접 기여하는 화면」입니다.

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 참여 화면 — 전역 카운터·단계 해금·개인 기여 (이 문서) | **구현** |
| 2 | 다른 게임이 판을 끝낼 때 기여 API 를 호출 | 미구현 |
| 3 | 단계 해금 시 전원 일괄 지급 · 푸시 | 미구현 |

2단계는 배포 22종의 `onRunEnd` 에 한 줄을 넣는 일이고, 3단계는 배치 작업이라 게임 추가
절차(A~D) 밖입니다. **이 문서의 범위는 1단계뿐입니다.**

---

## 2. 규격에서 벗어난 항목

| 항목 | 규격 | 이 게임 | 이유 |
|---|---|---|---|
| 성격 | 실력·판단으로 결과가 갈리는 게임 | **결과가 갈리지 않는다** | 기여는 누구나 같습니다. 게임이 아니라 참여 화면이라 킬 테스트 대상이 아닙니다 |
| 상태 | 판이 끝나면 사라짐 | **사용자 간 공용 상태** | ⑮ 다들 뭐 골랐을까에 이어 두 번째입니다 |
| 도전 기회 | 하루 5회 | 하루 **1회** (+광고 1회) | 하루 목표라 여러 번 참여할 것이 없습니다 |

`category` 는 `puzzle` 로 두었습니다. 반응속도·판단이 없어 `action`(순발력) 묶음에 두면
「빨리 해야 하는 게임」으로 읽히기 때문입니다.

## 3. 전역 카운터 — 원자성과 처리량은 다른 문제입니다

```sql
INSERT INTO gauge_daily (day, total, updated_at) VALUES (?, ?, ?)
ON CONFLICT(day) DO UPDATE SET total = total + excluded.total, ...
```

**이 증가는 원자적입니다.** 읽고 더해서 쓰는 방식이 아니라 한 문장이고, SQLite(D1)는
쓰기를 직렬화하므로 동시 기여에서 값이 유실되지 않습니다.

대규모에서 걸리는 것은 정확성이 아니라 **쓰기 처리량**입니다. 그 지점에서는 캐시 계층이나
Durable Objects 로 옮겨야 하고, 그때도 이 표의 뜻은 그대로입니다.

**토큰마다 쓰지 않습니다.** 판이 끝난 뒤 `onRunEnd` 에서 합계를 한 번 씁니다 — 한 판에
전역 쓰기가 토큰 수만큼 늘어나는 것을 피하기 위한 것이고, 화면에 필요한 「내 기여가
반영된 뒤의 값」은 지역 합으로 정확히 계산할 수 있습니다. 다른 사람의 기여는 다음
참여에서 보입니다.

## 5. 이름이 두 뜻을 갖지 않게

판정 응답의 `added` 는 **그 토큰 하나**의 증가분이고, `added_total` 은 **판 전체**의
기여입니다. 처음에는 둘 다 `added` 였는데 결과 화면이 조용히 토큰 하나의 값을 「내
기여」로 보여 주었고, 테스트가 거기에 걸렸습니다. 한 이름으로 두 뜻을 쓰지 않습니다.

## 6. 검증

`npm run test:api` 의 전용 시나리오(`gaugeFlow`)가 확인합니다.

- 토큰을 다 밀어 넣으면 끝난다(실패 없음)
- 기여가 **전역 게이지에 실제로 누적된다** — 다음 참여의 시작값이 올라가 있어야 합니다
- 「기여 2배」가 남은 토큰의 반영량을 두 배로 만든다
