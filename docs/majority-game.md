# ⑮ 다들 뭐 골랐을까 — 구현 명세

기획서 `PLAN-01 다들 뭐 골랐을까` (`IDEA-2026-0001-R1`, 안정형 / 엔진 B 선택·퀴즈)를
이 저장소의 아케이드 미니게임으로 구현한 문서입니다.

기존 14종과 규칙 체계는 같습니다 — 하루 도전 기회, 목숨, 광고 이어하기, `+` 리그, 백분위.
**다른 점은 정답의 출처 하나뿐입니다.** 나머지 게임의 정답은 서버가 그 자리에서 만든
난수지만, 이 게임의 정답은 **다른 사람들이 실제로 고른 결과**입니다.

---

## 1. 왜 이 게임인가 (기획서 2장 요약)

정답형 퀴즈는 정답 아카이브로 반드시 뚫립니다. 정답 공유 글이 12,386건 쌓여 매일
갱신되고, 캐시워크의 공식 판매 문구("정답 확인을 위해 광고주 페이지 방문이 필수적")를
아카이브가 그대로 무력화합니다. 광고주는 방문을 샀는데 이용자는 정답만 복사합니다.

기획서의 해법은 **정답을 사후에 결정하는 것** 입니다. 질문을 "무엇이 맞는가"에서
"오늘 사람들은 어느 쪽을 더 많이 골랐을까"로 바꾸면 미리 존재하는 정답이 없습니다.

> 기획서는 이것을 "아카이브 원천 불가능" 이라고 썼습니다. **이 구현에서는 그렇게까지
> 주장하지 않습니다.** 비율이 안정된 문항은 어제와 오늘의 답이 같을 수 있어서, 유통되면
> 그대로 쓰입니다. 실제로 달성한 것은 §6에 있는 그대로입니다 —
> **아카이브의 유효기간이 영구에서 하루로 줄고, 아카이브로 얻는 점수가 가장 낮습니다.**

---

## 2. 게임 규칙 (구현값)

| 항목 | 값 | 근거 |
|---|---|---|
| 진행 방식 | `ENDLESS` (문항마다 서버 판정) | 정답이 서버에만 있어야 합니다 |
| 성공 조건 | **3문항 연속 적중** | 기획서 6장 |
| 문항 제한 시간 | **10초** | 기획서는 7초 — §5 참조 |
| 목숨 | 1 (빗나가면 종료) | 기획서 6장 |
| 되돌리기(광고) | 1런당 **2회** | 기획서 8장 「방문당 광고 최대 2회」 |
| 기본 도전 기회 | 하루 5회 (+광고 5회) | 이 저장소 아케이드 공통 |
| 응답 시간 하한 | 1.5초 | 기획서 7장 |
| 리그 | `all` / `all+`(되돌리기 사용) | 이 저장소 공통 |

수치는 전부 `src/lib/config.js` 의 `ARCADE.MAJORITY` 한 곳에 있습니다.

### 한 판의 흐름

```
[ready]  최고 점수 · 오늘 남은 도전 · ▶시작        [광고: 기회 +1]
[play]   문항 1 → 즉시 결과 공개 → 문항 2 → 문항 3
[pause]  빗나감 → "되돌리기" 아니면 "여기서 끝내고 결과 보기"   [광고: 되돌리기]
[over]   점수 · 문항별 기록 · TOP N%              [광고: 전체 순위]
```

되돌리기는 **빗나간 문항을 새 문항으로 바꿔 잇습니다.** 이미 적중한 문항은 그대로입니다
(기획서 8장 「광고 후 진행 유지」). 광고를 거부하면 그 시점까지의 점수가 그대로 확정
저장됩니다(기획서 8장 「광고 거부 시 전액 확정 지급」).

## 3. 정답을 어떻게 정하는가 — 이 게임의 핵심

문항 하나는 표를 **두 벌** 가집니다 (`migrations/0007_majority_questions.sql`).

```
snap_a / snap_b   어제까지 확정된 누적 표   ← 판정은 이 값으로만 합니다
live_a / live_b   오늘 들어온 표            ← 자정(KST)에 snap 으로 이월
```

### 왜 실시간 집계를 정답으로 쓰지 않는가

기획서 4장은 "즉시 결과 공개 — 62%가 왼쪽을 골랐어요" 를 재미의 핵심으로 둡니다.
그런데 그 62%가 **오늘의 실시간 집계**이면 두 가지가 동시에 무너집니다.

1. **자기실현** — 다수를 따라가면 맞으므로, 비율이 공개될수록 그쪽이 더 다수가 됩니다.
   40:60을 노려 만든 문항이 90:10으로 수렴하고, 그러면 기획서 16장 위험 2(다수 쏠림)가
   설계로 예방되는 게 아니라 설계에 의해 **가속**됩니다.
2. **중간 결과 유통** — 오전 참여자가 결과 화면을 캡처해 올리면 오후 참여자는 그대로
   찍으면 됩니다. 문항을 읽을 필요가 없어지므로, 정답 아카이브와 정확히 같은 실패
   모드입니다. 기획서 16장에는 이 항목이 없습니다.

**오늘의 표가 오늘의 정답을 바꾸지 않게 하면** 1번이 사라지고, 2번은 "그 문항의 답이
내일 바뀔 수 있는" 형태가 됩니다. 그래서 판정 기준은 어제까지의 확정 집계입니다.
이월은 Cron(10분 주기)이 하루 한 번만 수행합니다 —
`rollDailySnapshot()`, `majority_roll` 테이블이 중복 실행을 막습니다.

### 판정 기준 세 가지 (`basis`)

| basis | 조건 | 판정 | 화면 표기 |
|---|---|---|---|
| `day` | 확정 표 ≥ 12 | 확정 집계의 다수 | "어제까지 N명 중 62%" |
| `live` | 확정 표 < 12 이고 확정+오늘 ≥ 12 | 합산 집계의 다수 | "지금까지 N명 중 62%" |
| `none` | 그래도 12 미만 | **판정 없이 통과 · 점수 0** | "아직 집계 중인 문항이라 통과했어요" |

기획서 16장 위험 1(초기 표본 부족)에 대한 답입니다. 기획서는 "결과 공개 유예 또는
**시드 데이터**"를 제시했는데, 시드는 쓰지 않았습니다. 실제로 아무도 고르지 않은 문항에
"62%가 이쪽을 골랐어요"라고 표시하면 그건 허위 표시이고, 나중에 실제 비율이 드러났을 때
숫자 전체의 신뢰를 잃습니다. **없는 숫자는 만들지 않고, 없다고 말합니다.**

동률(정확히 50:50)은 적중 처리합니다 — 사용자에게 불리한 쪽으로 반올림하지 않습니다.

### 쏠린 문항 자동 제외

다수 비율이 **85% 이상**이면 배정 후보에서 뺍니다(`SKEW_EXCLUDE_PCT`). 찍어도 맞는
문항은 게임이 아닙니다. 다만 문항이 모자라면(초기 운영) 채워서라도 판을 시작합니다 —
게임이 안 열리는 것보다는 낫고, 그런 문항은 점수가 낮아 자연히 손해입니다.

## 4. 점수 — "찍기"와 실력을 가르는 장치

```
문항 점수 = 100 − 2 × (다수 비율 − 50)      50:50 → 100점 · 62:38 → 76점 · 90:10 → 20점
판 점수   = Σ(적중 문항 점수) + 완주 보너스 50점
순위 지표 = −판 점수                        (엔진 규약: 작을수록 상위)
```

**팽팽한 문항을 맞힐수록 높은 점수** 입니다. 이 한 줄이 기획서의 위험 두 개를 함께 막습니다.

- **위험 3 「찍기 인식」** — 찍기는 어떤 문항에서도 기대값이 절반입니다. 반면 판단이 되는
  사람은 50:50에 가까운 문항에서 차이를 냅니다. 그 차이가 그대로 점수 차가 됩니다.
- **아카이브 유인** — 외워 올 만큼 답이 고정된 문항은 곧 쏠린 문항이고, 쏠린 문항은
  점수가 가장 낮습니다. **아카이브로 얻는 이득이 구조적으로 가장 작습니다.**

완주 보너스는 「집계된 문항을 한 번이라도 맞힌」 판에만 붙습니다. 전부 `none` 이었던 판이
50점을 받으면 안 됩니다.

## 5. 기획서와 다르게 구현한 부분

| 항목 | 기획서 | 구현 | 이유 |
|---|---|---|---|
| 정답 기준 | 오늘의 실시간 집계 (즉시 "62%" 공개) | **어제까지의 확정 집계** | 실시간 집계를 정답으로 쓰면 자기실현으로 쏠림이 가속되고, 중간 결과 공유가 정답 아카이브와 같은 역할을 합니다 (§3) |
| 문항 제한 시간 | 7초 | **10초** | 기획서 15장의 첫 번째 검증 가설이 "예측형이 정답형보다 **문항 열람 시간**이 길다"입니다. 7초는 그 지표에 천장을 씌웁니다. 선택지가 광고주 상품이 되면(10장) 더 걸립니다. 문항별 응답 시간은 `results.detail_json.picks[].ms` 에 남으므로 실제 분포를 보고 조정하면 됩니다 |
| 표본 부족 대응 | 결과 공개 유예 **또는 시드 데이터** | 시드 없이 「집계 중」 통과 | 없는 비율을 지어내 표시하는 것은 허위 표시입니다 (§3) |
| 세션 제한 | 계정당 **1일 1세션** | 판은 하루 5+5회, **표는 하루 첫 판만 집계** | 1일 1세션의 목적은 한 사람이 같은 문항에 여러 번 투표해 비율을 흔드는 것을 막는 것입니다. 그 목적은 표 쪽에만 걸면 달성되고, 그러면 이 저장소의 재도전 구조(광고 이어하기)가 유지됩니다 |
| 응답 시간 하한 | 1.5초 (악용 방지) | 1.5초 — **판정은 하되 표로 세지 않음** | 하한 미만이라고 판을 거부하면 정상 사용자가 손이 미끄러진 것까지 막습니다. 오염되면 안 되는 것은 순위가 아니라 **비율** 이므로, 그 표만 버립니다. 판정에 쓰는 시간은 클라이언트 신고값이 아니라 서버가 라운드를 발급한 뒤 흐른 시간입니다 |
| 보상 | 포인트(1P·2P·5P·등급) | 점수 + 리그 순위 | 이 저장소에는 포인트 경제가 없습니다. 보상 구조는 그대로 점수 구조로 옮겼습니다 (참여 보상 = 진입만 해도 기록이 남음 / 적중 = 문항 점수 / 3연속 = +50) |
| 재방문 장치 | 일일 기록 + **월 누적 등급** | 개인 최고 점수 + 일일 도전 기회 | 월 단위 등급은 게임이 아니라 앱 단위 설계입니다 (`docs/arcade-10-games.md` §11 과 같은 판단) |
| 문항 배정 | 하루 공통 문항 | **사용자마다 무작위 배정** | 같은 시각 모두가 같은 문항을 보면 유통 한 건이 그 시간대 전체에 유효해집니다. 은행에서 6문항을 무작위로 뽑고 보기의 좌우도 매번 섞습니다 |

## 6. 어뷰징 방지와 남아 있는 한계

### 서버가 실제로 막는 것

- **정답 비노출** — 집계 비율은 문항과 함께 내려가지 않습니다. 판정이 끝난 응답에만
  들어갑니다. (`npm run test:abuse` 「판정 전 다수 비율 노출」)
- **판정은 전부 서버** — 클라이언트는 "몇 번째 보기를 눌렀는가"만 보냅니다.
  문항 묶음과 그 시점의 집계는 세션에 **암호화**되어 저장됩니다(AES-256-GCM).
- **좌우 위치 무작위** — "왼쪽"이라는 한 단어로는 답을 공유할 수 없습니다.
- **표 오염 차단** — ① 하루 첫 판만 집계 ② 응답 하한(1.5초) 미만은 미집계
  ③ 시간 초과(선택 없음)는 미집계 ④ 결과가 저장된 뒤에만 반영되므로 중복 제출로
  같은 표가 두 번 들어가지 않습니다.
- **기록 중복·시간 조작** — 기존 공통 방어(세션 소유권, `results.session_id` UNIQUE,
  서버 관측 시간창)를 그대로 씁니다.

### 남아 있는 한계 (정직한 기록)

- **비율이 안정된 문항은 여전히 유통될 수 있습니다.** 하루가 지나면 아카이브 한 줄은
  무효가 되지만, 누적 표가 충분히 쌓인 문항은 어제와 오늘의 다수가 같을 가능성이
  높습니다. 실질 방어는 세 가지 조합입니다 — 문항 무작위 배정 · 은행을 계속 늘리는 운영 ·
  **쏠린 문항일수록 점수가 낮은 설계**(§4). "원천 불가능"이 아니라 "실익이 작다"입니다.
- **자동화 스크립트는 막지 않습니다.** 다만 이 게임에는 알아낼 정답이 없어서, 스크립트가
  할 수 있는 최선은 찍기(기대 적중률 50%)입니다. 기존 게임(암산·스트룹)과 달리
  **자동화의 실익이 원리적으로 작습니다.**
- **이탈한 판의 표는 들어가지 않습니다.** 표는 결과가 확정될 때 한 번의 batch 로
  반영합니다. 브라우저를 그냥 닫으면 그 판의 선택은 집계되지 않습니다 — 라운드마다
  쓰면 왕복이 한 번 더 늘고, 그 비용이 이 편향보다 큽니다.
- **문항 은행이 작으면 같은 문항을 다시 만납니다.** 현재 74문항이고, 한 판에 최대 6문항이
  나갑니다. 기획서 2장이 지적한 "문항 은행 고갈"은 이 게임에서 훨씬 느리게 오지만
  (같은 질문도 날짜가 다르면 결과가 달라집니다) 0은 아닙니다.
- **표 갱신의 쓰기 경합.** 인기 문항 몇 행에 쓰기가 몰립니다. D1(SQLite)은 단일 기록자라
  대규모 트래픽에서는 이 지점이 먼저 막힙니다. 넘으면 문항별 집계를 Durable Object 나
  Queue 로 옮기는 것이 정석입니다 (`docs/arcade-10-games.md` §10.4 와 같은 결론).

## 7. 광고 구조 (기획서 8장 대응)

| 기획서 | 구현 |
|---|---|
| 광고 없이 3문항 전부 가능 | ✔ 기본 도전 기회로 광고 없이 완주할 수 있습니다 |
| 첫 광고 = 빗나간 직후, 선택 | ✔ `MAJORITY_BOOST` — 실패 화면에만 노출 |
| 광고 혜택 = 되돌리기 1회 | ✔ 목숨 +1 · 적중분 유지 · 새 문항으로 이어감 |
| 최대 2회 / 방문 | ✔ `boostsPerRun: 2` (서버가 세션 기준으로 강제) |
| 광고 거부 시 획득분 전액 확정 | ✔ 「여기서 끝내고 결과 보기」 → `/game/finish` |
| 게임 시작 전 강제 광고 없음 | ✔ 기존 원칙 그대로 |

「되돌리기」 카드는 「다시 도전하기」보다 **아래**에 둡니다. 무료 재도전 경로를 가리면
단기 광고 수익은 늘지만 리텐션이 떨어집니다 (`docs/arcade-10-games.md` §3.4).

기획서 부록 **AB-1**(되돌리기 vs 보상 2배)은 이 구조에서 그대로 실험할 수 있습니다 —
`spec.applyBoost` 만 바꾸면 됩니다.

## 8. 운영

### 문항 추가·수정

문항의 단일 출처는 `scripts/gen-majority-questions.mjs` 입니다. 질문 길이(24자)·보기
길이(12자)·중복을 이 스크립트가 검증하므로, **어느 경로로 넣든 배열에는 반드시 함께
추가합니다** — 새 환경을 처음부터 구축할 때 쓰이는 것이 이 배열입니다.

```bash
# scripts/gen-majority-questions.mjs 의 배열을 편집한 뒤
node scripts/gen-majority-questions.mjs
```

**주의 — 이미 마이그레이션을 적용한 DB(운영 포함)에는 이것만으로 반영되지 않습니다.**
`0008` 은 적용 이력이 남아 있어 내용을 바꿔도 다시 실행되지 않습니다. 그래서 경로가
DB 상태에 따라 갈립니다.

| 상황 | 방법 |
|---|---|
| 아직 적용 전 (새 환경 · 로컬 초기화) | 스크립트 재생성만으로 충분합니다 |
| 이미 적용됨 (운영 · 개발 중인 로컬) | **새 마이그레이션 파일**에 추가분만 `INSERT` 합니다 |

```sql
-- migrations/0009_add_majority_questions.sql
INSERT INTO majority_questions (topic, prompt, option_a, option_b, active, created_at) VALUES
  ('food', '피자에 파인애플은?', '좋다', '싫다', 1, unixepoch() * 1000);
```

이미 있는 문항을 다시 넣지 않도록 주의하세요. `prompt` 에는 UNIQUE 제약이 없습니다 —
같은 질문이 두 행이 되면 표가 둘로 갈려 양쪽 다 표본이 모자란 상태가 됩니다.
넣기 전에 확인하는 것이 확실합니다.

```bash
npx wrangler d1 execute minigames-db --remote --command \
  "SELECT prompt FROM majority_questions WHERE prompt IN ('피자에 파인애플은?');"
```

> 같은 제약이 타이핑 문장 DB(`0002_seed_sentences.sql`)에도 있습니다. 저장소가 처음
> 만들어질 때부터 그랬고, 이 게임에서 처음 문제가 드러났습니다.

**광고주 문항**(기획서 10장 「선택지 자체가 광고주 상품」)은 기간이 정해져 있어 스크립트
배열이 아니라 위와 같은 운영 경로로 넣습니다. `topic` 을 `'sponsor:<브랜드>'` 로 두면
배정·판정 규칙은 완전히 동일하고, 기간이 끝나면 `active = 0` 으로 내립니다.

문항을 내릴 때는 **지우지 말고 `active = 0`** 으로 둡니다 — 쌓인 표를 잃지 않습니다.
지웠다가 같은 질문을 다시 넣으면 표본이 0인 문항이 되어 「집계 중」으로 돌아갑니다.

### 운영자가 조정하는 값 (기획서 13장 「운영자 변경 데이터」)

| 값 | 위치 | 의미 |
|---|---|---|
| `MIN_SAMPLE` | `config.js` | 이 표 수를 넘겨야 비율을 결과로 씁니다 (기본 12) |
| `SKEW_EXCLUDE_PCT` | `config.js` | 쏠림 자동 제외 임계값 (기본 85%) |
| `LIMIT_MS` `MIN_ANSWER_MS` | `config.js` | 문항 제한 시간 · 응답 하한 |
| `CLEAR_BONUS` | `config.js` | 완주 보너스 |
| 문항 은행 | `majority_questions` | 문항 추가·중지 |

### 로컬에서 확인할 때

문항 은행은 표가 0인 상태로 시작하므로, 방금 마이그레이션한 로컬 DB 에서는 모든 문항이
「집계 중」으로 나옵니다(정상입니다 — §3). 점수·비율 공개 화면까지 보려면 표를 넣어 둡니다.

```bash
npx wrangler d1 execute minigames-db --local --command \
  "UPDATE majority_questions SET snap_a = 62, snap_b = 38 WHERE id % 2 = 0;
   UPDATE majority_questions SET snap_a = 30, snap_b = 70 WHERE id % 2 = 1;"
```

**로컬 전용입니다.** 운영 DB 에 이런 값을 넣으면 지어낸 비율을 사용자에게 실제 집계라고
보여 주는 것이 됩니다 — 이 게임이 하지 않기로 한 바로 그 일입니다.

### 집계 상태 확인

```bash
npx wrangler d1 execute minigames-db --remote --command \
  "SELECT prompt, snap_a, snap_b, live_a, live_b FROM majority_questions ORDER BY snap_a+snap_b DESC LIMIT 10;"
```

### 공통 엔진에 추가한 것 (`src/lib/arcade.js`)

다른 게임의 정답은 서버 난수라 순수 함수로 만들 수 있지만, 이 게임은 DB 를 읽어야
합니다. 그래서 훅 세 개를 **선택 항목으로** 넓혔습니다. 기존 10종은 한 줄도 바뀌지 않습니다.

| 훅 | 용도 |
|---|---|
| `initSecret(meta, ctx)` — `await` + `ctx` | 런 시작 시 문항 6개와 집계를 **한 번에** 읽습니다. 라운드마다 읽으면 왕복이 한 번 더 늘어납니다 |
| `makeRound(roundNo, meta, secret)` — 3번째 인자 | 미리 뽑아 둔 문항 묶음에서 꺼내 씁니다 |
| `detailOf(meta)` | ENDLESS 는 채점이 라운드마다 흩어져 있어 상세 기록을 넘길 자리가 없었습니다 |
| `onRunEnd(env, meta, ctx)` | 결과가 저장된 뒤 이 판의 표를 한 번의 batch 로 반영합니다 |

한 판에 6문항을 미리 뽑는 이유: 목숨 1 + 되돌리기 2 = 최대 3번 빗나갈 수 있고 적중은
3번 필요하므로, 한 판에서 나갈 수 있는 문항은 최대 6개입니다.
