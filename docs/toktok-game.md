# ㉘ 톡톡 — 구현 명세

기획서: `../reward-minigame-research/plans/2026-07-31/PLAN-22_톡톡.md` (IDEA-2026-0022)

> 화면 가득한 뽁뽁이를 **손을 떼지 않고 훑어서** 연달아 터뜨립니다.
> 손을 떼는 순간 판이 끝나고, 그때까지 이어 터뜨린 개수가 기록입니다.

아케이드 규격(1판 10~60초 · 조작은 탭 1종류 · 단일 세션 완결 · 광고 트리거 3종)을
두 항목에서 벗어나므로 `CLAUDE.md` B-3 에 따라 이 문서를 둡니다.

---

## 1. 규격을 벗어난 것

| 항목 | 규격 | 이 게임 | 이유 |
|---|---|---|---|
| 조작 | 탭 1종류 | **연속 드래그** (손을 뗄 때까지 한 번) | 기획의 핵심이 원리 2 손맛(톡 터지는 촉감)이고 **종료 조건 자체가 「손을 뗌」**입니다. 탭으로 바꾸면 게임이 통째로 남지 않습니다 |
| 사운드 | 27종에 없음 (`arcade-10-games.md` §11 — WebView 브리지 대기) | **WebAudio 로 직접** | 끊기지 않는 동안 소리가 반음씩 오르는 것이 원리 4(콤보·흐름)의 유일한 표현이고, 기획서 16장이 최상위 위험으로 든 것도 이것입니다. 브리지 없이 웹에서 되는 일이라 기다릴 이유가 없습니다 |

한 판 길이(5~15초)는 규격의 10~60초 **안쪽 하한에 붙어** 있습니다. 이어하기 2회를 쓰면
광고 포함 약 1분입니다.

### 대체 경로 (드래그를 못 쓰는 경우)

방향키로 훑고 `Enter`/`Space` 로 손을 뗍니다. 첫 방향키 입력이 판 한가운데를 터뜨리며
훑기를 시작합니다. 마우스가 없는 사용자가 같은 게임을 할 수 있어야 하고, 키보드 경로만
이상치로 표시되는 일이 없도록 궤적 검사에 칸당 시간 하한을 두지 않았습니다(§4).

## 2. 라운드 = 한 번의 훑기

터짐 하나마다 서버에 물으면 판이 성립하지 않습니다 — 라운드 왕복이 약 470ms 인데
터짐은 초당 8~10회입니다(`arcade-10-games.md` §10.3).

그래서 화면은 훑는 동안 지나간 칸과 시각을 모아 두었다가 **조각 단위로** 보냅니다
(아래 참조). 판을 끝내는 것은 손을 뗀 마지막 조각뿐입니다.

```
answer = { cells: [칸 번호 …], times: [조각 시작 이후 ms …], ongoing: boolean }
                    -1 = 손이 판 밖으로 나갔다 돌아온 이음매
```

### 한 번의 훑기가 여러 조각으로 온다 (PC 마우스 확인에서 나온 것)

초안은 훑기 하나를 **요청 하나**로 받았습니다. 기획서 §0-I 이 「최대치가 존재하지
않는다」고 쓴 근거는 손목이 화면 끝에 닿아 저절로 손을 떼게 된다는 것이었는데,
**마우스에는 그 제약이 없습니다.** 버튼을 누른 채 판 위를 계속 돌리면 훑기가 몇 분이고
이어집니다.

그 결과 실제로 이렇게 됐습니다.

```
화면이 센 것  2000개
서버 기록      400개   ← MAX_POPS 에서 잘림. 사용자에게 아무 표시도 없음
요청 크기      18KB
```

그래서 화면이 `FLUSH_AT`(150)개마다 **조각**을 보냅니다. 조각은 `ongoing: true` 로
판을 끝내지 않고 누적만 하며, 손을 뗀 마지막 조각(`ongoing: false`)이 판을 끝냅니다.
**규칙은 그대로입니다 — 끝내는 것은 여전히 손을 떼는 것뿐입니다.**

- 화면은 조각을 보내는 즉시 버퍼를 비우고, 날아가는 동안에도 다음 조각을 채웁니다.
  표시 개수는 `서버 확인분 + 날아가는 중 + 아직 안 보낸 것` 세 값의 합이라 조각을
  보내는 순간에도 숫자가 뒤로 가지 않습니다.
- 조각의 시각은 **조각 시작 기준**입니다. 서버의 시간창 검사가 조각마다 성립해야 합니다.
- 훑는 도중 도착한 새 판(라운드)은 상품 순번만 바꾸고 **화면을 다시 그리지 않습니다.**
  손이 붙어 있는데 판을 갈아엎으면 훑기가 끊깁니다.
- `best_stroke`(한 번에 최다)는 조각이 아니라 **훑기 단위**로 셉니다(`ext.cur`).
- 이상치 판정도 **조각의 비율**로 봅니다. 긴 훑기는 조각이 열 개를 넘으므로 하나만
  걸려도 이상치로 보면 오래 훑은 사람이 걸립니다.

> 남는 것 하나: 조각이 날아가는 약 0.3초 동안 터진 칸은 **다음 조각의 상품 순번**에
> 속하는데 화면은 그 스케줄을 아직 못 받았습니다. 그 몇 개는 상품이 화면에 드러나지
> 않고 개수만 다음 판정에서 맞춰집니다. 기록은 늘 서버 기준이라 틀어지지 않습니다.

손을 뗀 것이 곧 **소진**이라 `lives: 1` 입니다. 엔진의 「목숨 소진 → 세션 유지 →
이어하기 대기」 흐름이 기획서 8장의 「그 자리에서 이어서 할래요?」와 같은 모양이기
때문입니다(⑳ 슥슥 긁기와 같은 처리). **실패로 표시되는 곳은 화면 어디에도 없습니다.**

한 판 = 무료 1스트로크 + 광고 2스트로크, 최대 3번입니다.

## 4. 궤적 검사 — 서버가 실제로 막을 수 있는 것

| 검사 | 막는 것 |
|---|---|
| **경로 인접성** | 연달아 터진 두 칸은 반드시 이웃이어야 합니다. 손가락은 연속이기 때문입니다. 어긋난 지점에서 기록을 자릅니다 |
| **시간창** | 신고한 시각이 서버가 라운드를 발급한 뒤 흐른 시간(+3초)을 넘으면 그 뒤는 세지 않습니다 |
| **지속 속도** | 스무 칸 넘게 초당 60칸을 유지하면 이상치(`suspect`) |
| **간격의 균일함** | 간격 24개 이상이 모였을 때 변동계수가 0.03 미만이면 등속 = 이상치 |

인접성 검사는 클라이언트에 **선분 보간을 강제**하는 효과도 있습니다. 기획서 16장 위험 2
(「빠른 드래그에서 히트가 새는 문제」)를 빠뜨린 구현은 기록이 그 자리에서 잘립니다.

### 브라우저 확인에서 잡힌 오탐 — 칸당 시간 하한은 쓸 수 없다

초안은 다른 게임처럼 **칸 하나당 최소 시간**(25ms)에 비율 판정을 걸었습니다.
브라우저에서 실제로 훑어 보니 정상 플레이가 그대로 이상치로 찍혔습니다.

원인은 두 가지였고 둘 다 정상 동작입니다.

1. 한 번의 `pointermove` 로 두세 칸이 터지는데 **시각이 전부 같아** 간격이 0ms 이 됩니다.
   → 클라이언트가 보간한 칸에 **시각도 나눠 적도록** 고쳤습니다. 손가락은 그 사이를
   실제로 지나갔으므로 그렇게 적는 것이 사실에 맞습니다.
2. 그렇게 고쳐도 빠른 훑기는 칸당 10~20ms 입니다. 칸 하나가 화면에서 약 9mm 이고
   손가락 최고 속도가 1~2 m/s 이므로, **칸당 시간 하한은 손가락이 빠른 사람만
   순위에서 빼는 판정**이었습니다. → 하한을 없애고 스트로크 전체의 **평균 속도**로
   바꿨습니다(초당 60칸).

회귀 검사는 `scripts/test-api.mjs` 의 `toktokStrokeRules` 에 있습니다.

### 남는 한계 (정직하게)

- **매크로를 원리적으로 막지 못합니다.** 사람처럼 흔들리는 간격으로 이웃 칸을 잇는
  경로를 만들면 서버가 구별할 수단이 없습니다. 기존 게임과 같은 판단입니다
  (`arcade-10-games.md` §6 — 이상치 표시로만 대응하고, 광고 보상은 판정 결과가 아니라
  시청 여부에 걸려 있어 랭킹 조작의 실익이 수익에 닿지 않습니다).
- **경계에서 손가락을 떠는 것**(두 칸을 오가는 것)도 터짐으로 셉니다. 훑는 것보다
  유리하지도 않고(속도가 비슷합니다) 막으려면 지그재그 훑기까지 함께 막게 되어
  두지 않았습니다. 재도전률·평균 연속이 기획서 예상과 크게 어긋나면 그때 봅니다.

## 5. 손이 화면에 닿아 있는 순간 (0-H)

⑳ 에서 실서비스로 겪은 것과 같은 자리입니다. 판이 끝나는 조건이 「손을 뗌」이라,
화면이 [pause] 로 바뀐 직후에 **다시 손을 대려는 동작**이 그 자리에 온 광고 카드를
누릅니다. 기획서 8장의 「광고는 선택형」이 그 자리에서 깨집니다.

- [pause] 화면 전체를 **400ms 동안** `pointer-events: none` 으로 둡니다
  (⑳ 은 광고 카드만 막았는데, 「여기서 끝내고 결과 보기」도 같은 위험이 있어 화면째 막습니다).
- 손을 뗀 뒤 판정 왕복 동안 판을 잠가(`.is-locked`) 새 훑기가 시작되지 않게 합니다.
- 좌표를 만들 수 없는 순간(숨은 요소의 rect 가 0×0)에는 좌표를 만들지 않고 멈춥니다.
- 보간 횟수에 상한을 둡니다(격자가 유한해 닿지 않지만 루프 종료를 보장합니다).

## 6. 터짐 연출

기획서 16장이 최상위 위험으로 든 것이 **연출이 값싸면 게임이 통째로 죽는다**입니다.
초안은 PC 확인에서 「너무 작고 약하다」는 판정을 받아 약 2배로 키웠습니다.

| | 초안 | 지금 |
|---|---|---|
| 부푸는 폭 | 1.18배 | **1.6배** |
| 길이 | 150ms | 240ms (부풀고 → 잠깐 머물고 → 꺼짐) |
| 밝기 | 1.7 | 1.95 + 채도 1.35 — **색은 남깁니다.** 흰색까지 날리면 뽁뽁이가 흰 덩어리가 됩니다 |
| 파동 | 없음 | 칸 밖으로 2.6배까지 퍼지는 링(`.bub__ring`) |
| 밀려 올라옴 | 0.7 → 1 | 0.55 → 1.12 → 1 (살짝 넘겼다 자리잡음) |
| 상품 등장 | 1.25배 | 1.8배 · 더 높이 떠오름 |

터지는 칸은 `z-index: 5` 로 이웃 위에 올립니다. 파동이 옆 칸 아래로 깔리면 퍼지는
느낌이 죽습니다.

## 7. 저장하는 것 · 저장하지 않는 것

**마이그레이션이 필요 없습니다.** 판이 끝나도 남는 상태가 없습니다.

- 최장 연속은 `results` 의 `rank_metric`(= `-(터뜨린 개수)`)으로 남습니다.
- 「오늘의 포장」은 날짜를 해시해 고르므로 저장할 것이 없고, 같은 날 접속한 모든
  사용자가 같은 포장을 봅니다.
- 상세 기록(`detail_json`)은 그 판 직후 결과 화면에만 쓰이므로
  `RESULT_DETAIL_KEEP` 에 넣지 않았습니다.

## 8. 순위 지표에 속도 보정이 없는 이유

다른 연속형 게임은 동점자를 평균 응답 시간으로 가릅니다(`streakMetric`).
이 게임에는 넣지 않았습니다 — 넣으면 **빨리 끄는 쪽이 유리**해져 기획서 0절의
「빠르게 끄는 것이 아니라 끊지 않는 것이 과제」가 뒤집히고, 15장 가설 4
(빠른 이용자와 느린 이용자의 기록 차이가 작다)를 잴 수 없게 됩니다.

## 9. 운영자가 바꾸는 값

전부 `src/lib/config.js` 의 `ARCADE.TOKTOK` 입니다.

| 값 | 뜻 |
|---|---|
| `COLS` `ROWS` | 판 크기 = 뽁뽁이 밀도 |
| `FLUSH_AT` `MAX_POPS` | 조각 하나의 크기와 상한. 화면(`FLUSH_AT` 상수)과 **같은 값이어야 합니다** |
| `PRIZE_EVERY` `PRIZE_JITTER` | 상품 뽁뽁이가 나오는 간격 |
| `PRODUCTS` | 상품 뽁뽁이 안에 드러나는 것 = **광고 지면**. 브랜드 주간에는 이 배열만 갈아 끼웁니다 |
| `PACKS` | 「오늘의 포장」 무늬·색 세트. 브랜드 패턴을 넣는 자리입니다 |
| `baseAttempts` `adAttemptsPerDay` `boostsPerRun` | 하루 기회·광고 한도 |

> **원가 레버로 쓰지 않습니다** (기획서 7장 · 안티패턴 4번).
> 뽁뽁이 밀도와 상품 등장 확률은 재미의 값이지 원가의 값이 아닙니다.
