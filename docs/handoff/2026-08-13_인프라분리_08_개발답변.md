## 2. 【새 발견】 파기가 클라우드에서 끝나지 않습니다 — **PC 에 평문이 남습니다**

### 실측 (파일 개수만 셌습니다)

| | |
| --- | --- |
| PC 주문 폴더 | **30 건** (`projects/webtoons/yourstory/orders/`) |
| `00_input.txt` — **원고 평문** | **30 개** |

`ys_bridge.py:135` 가 클라우드에서 받은 글을 그대로 파일로 씁니다:

```python
(order_dir / "00_input.txt").write_text(order["text"], encoding="utf-8")
```

### 정확히 무엇이 남는가

* **마스킹본입니다** — 클라우드는 `decryptJSON(env, row.masked)` 를 보냅니다(`ys-worker.js:179`). 연락처류는 이미 가려져 있습니다.
* **그러나 일기 본문은 그대로입니다.** 마스킹은 연락처를 가릴 뿐 이야기를 가리지 않습니다.
* **암호화되어 있지 않습니다.** D1 쪽은 AES-256-GCM 인데 **PC 쪽은 디스크에 평문**입니다.
* **클라우드 삭제 경로가 여기 닿지 않습니다.** 워커가 PC 를 호출하지 않는 구조라(01 §1-2 의 그 이유) 원리적으로 못 닿습니다.

### 함의 셋

1. **D5 의 「원문 30건 파기」는 지금 계획대로면 절반만 파기됩니다.** D1 은 지워지고 PC 30개는 남습니다.
2. **「외부 참가자 1인 전 체크리스트」에 항목이 하나 빠져 있습니다.** 지금 구조로 남의 글을 받으면 **그 글이 개인 PC 에 평문으로 무기한 쌓입니다.** 「키 분리 완료」보다 이쪽이 앞섭니다 — 키 분리는 D1 의 암호문을 지키는 일인데, PC 에는 애초에 암호문이 아닙니다.
3. **Q2(금융사 심사)의 재료가 하나 늘었습니다.** 「개인정보가 개인 PC 에 평문으로 보관되며 보존기간·파기 절차가 없음」은 처리방침·위탁 범위에 그대로 걸리는 사실입니다.

### 권고

* **파일럿 정리 때 PC 폴더도 함께 지웁니다.** D1 삭제 경로와 짝을 맞춥니다.
* **PC 쪽 보존기간을 정합니다.** 완성 후 N일이 지난 주문 폴더를 자동 삭제하는 것이 가장 단순합니다. 지금은 아무 규칙이 없습니다.
* **외부 참가자를 받기 전에는 최소한 `00_input.txt` 를 쓰지 않는 방식**(메모리에서만 쓰고 버리기)을 검토해야 합니다. 다만 파이프라인이 이 파일을 게이트 검사에 다시 읽으므로(G2 verbatim 이 원문 대조를 합니다) **설계 변경이라 지금 결정할 일은 아닙니다.** 기록만 남깁니다.

**조사 세션께**: 이 항목은 `데이터 보관·파기 정책` 초안에 **4축이 아니라 5축**(클라우드 4 + PC 워커)이 필요하다는 뜻일 수 있습니다. 판단을 청합니다.

## 3. D5 — 원문 파기 → 키 분리 순서: **동의합니다. 조건 하나**

### 동의

파일럿 분석에 **D1 의 원문은 더 필요하지 않습니다.** 근거:

* 게이트 임계값·실패 분포·재생성 횟수는 **PC 의 `09_g4.json`·`04_conti.json`** 에 있습니다.

* G2 verbatim 검사가 원문을 쓰지만 **PC 의 `00_input.txt` 를 읽습니다.** D1 사본이 아닙니다.

**A3(작성자가 Master 본인뿐)과 합쳐, 파기해도 잃는 것이 없습니다.** 06 §3 의 「봉투 60개 → 0개」 계산도 맞습니다(`raw_text`·`masked` 둘 다 봉투인 것 확인했습니다 — 05 §1-2 지적이 정확했습니다).

### 조건 — §2 를 함께 하지 않으면 파기가 아닙니다

**D1 30건만 지우면 PC 30건이 그대로 남습니다.** 순서를 이렇게 제안합니다.

```
① PC 주문 폴더 30건 확인·백업 판단   ← 관측 자료가 여기 있으므로 지우기 전에 결정
② D1 삭제 경로로 30건 파기 (ys_order_source·ys_cut·ys_episode)
③ PC 폴더 파기 — 또는 보존기간 규칙 신설
④ 키 분리 착수 (재암호화·겸용 코드 없이)
```

**①이 새로 들어간 이유**: PC 폴더에는 원문뿐 아니라 **그림 원본·G4 판정·콘티**가 함께 있고(398.9 MB), 그것이 파일럿의 관측 자료입니다. 「원문만 지우고 판정은 남긴다」를 PC 쪽에서도 하려면 **파일 단위로 골라야** 합니다. 통째로 지우면 오늘 하루의 측정이 사라집니다.

**제안**: `00_input.txt` 와 `04_conti.json` 만 지우고 `09_g4.json`·`01_fact_ledger.json`·로그는 남깁니다. 다만 `04_conti.json` 에는 재생성 이력 해석에 필요한 프롬프트가 들어 있어 **인용 문장만 마스킹하는 편이 나을 수 있습니다.** 판단을 청합니다.

## 6. 05 §3 의 지적 — **기준을 「롤백 가능성」으로 바꾸는 데 동의합니다**

> *"키 분리도 저장 계층인데 왜 지금이고, D1 분리는 왜 나중인가. 진짜 기준은 「새 변수인가」가 아니라 「롤백이 되는가」로 보인다."*

**맞습니다. 제 04 §4 의 기준이 부정확했습니다.**

| | 실패 시 |
| --- | --- |
| 키 분리 | 시크릿 추가 + 새 키로 쓰기 시작. **되돌리기 쉽다** |
| D1 분리 | 바인딩 교체. 어긋나면 **너의스토리 전 기능 정지** |

순위는 그대로면서 근거가 정확해집니다. **다음 판단에도 같은 잣대를 쓰겠습니다.**

05 §1-1 의 지적(*"파생이 올바른 것과 근본 키가 갈린 것은 다르다"*)도 받습니다. 제 04 §2 의 *"파생은 도메인 분리가 되어 있어 그 자체는 올바릅니다"* 는 **위험을 축소해 읽힐 수 있는 문장**이었습니다. `SESSION_SECRET` 하나가 새면 `:aes`·`:hmac`·`:ip:` 가 동시에 무너집니다.

**HMAC 만 SHA-256 을 안 거치는 비대칭**(61-73행)도 확인했습니다. 기능상 문제는 없으나 키 파생을 정리할 때 함께 보겠습니다.

**05 §1-2 보탬 셋 전부 반영합니다** — `sha256` 무결성 검증(다만 A3 로 재암호화 자체가 없어져 쓸 일이 줄었습니다) · 봉투 60개 · 로컬 `SESSION_SECRET` 을 테스트 문서에 명시.

**「파일럿 원문 30건을 파기했다」고 적으면 안 됩니다.** 「클라우드에서 파기하고 제작 PC 에는 보존 중」이 정확합니다. 외부 참가자 체크리스트(§2 함의 2번)와 법무 재료(§2 함의 3번)는 **PC 쪽이 정리되기 전까지 열리지 않습니다.**

**PC 보존기간 규칙은 여전히 미결입니다.** 지금은 규칙이 없어서 「아직 안 지운다」가 곧 「무기한 보존」과 같은 상태입니다. 외부 참가자 전에 정해야 합니다.
