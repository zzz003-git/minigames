## 2. Master 확정 — 도메인 분리 시점은 **「제휴 접촉 전」**

**제 03 문서 §3-2 의 「도메인 분리 견적이 빠졌다」 지적을 Master 판단으로 정정합니다.**

Master 지적: 이 도메인에는 **미니게임 · 오늘의나 · 웹툰** 세 축이 들어가 있고, 라이브 시점이 미정이며, 컨텐츠는 계속 늘어나고, **라이브 시점에 분리 작업도 함께 진행될 예정**입니다. 지금 한 도메인을 쓰는 것은 **개발·테스트가 편해서**입니다.

**저는 「지금이 가장 싸다」고 썼는데, 그것은 D1 분리의 논거를 도메인에 잘못 옮긴 것이었습니다.**

| | 시간이 가면 비싸지는가 |
| --- | --- |
| 데이터 이관량 | **아니오** — 라이브 전이면 버리면 됩니다 |
| 코드 결합도 | **예** — 다만 이건 Worker·D1 얘기이고 도메인과 별개입니다 |
| 도메인 분리 작업 | **아니오** — 라우팅·쿠키·정적자산 정리라 **언제 해도 2~3일** |
| 대외 노출 | **제휴 접촉 시점에 고정** ← 여기가 진짜 기한 |

> **확정: 지금은 한 도메인을 유지합니다. 착수 신호는 「제휴 접촉 개시」입니다.**
> 날짜가 아니라 **사건**에 묶었으므로 라이브 시점이 미정이어도 흐려지지 않습니다.

**Q1(Worker 분리) 순위는 그대로 유지**하시면 됩니다. 다만 사유가 「외부 공개 직전」에서 **「제휴 접촉 개시 시점」**으로 바뀝니다 — 제휴 접촉이 라이브보다 먼저 올 수 있습니다.

## 3. 【작업이 줄어듭니다】 파일럿 원문을 먼저 파기하면 키 분리가 가벼워집니다

**Master 확인: 현재 너의스토리 테스트 작성은 Master 본인만 하고 있고, 그 내용은 삭제해도 무방한 자료입니다.**

D1 실측으로 뒷받침됩니다 — 초대코드 **3개 발급·3개 등록**, 주문을 낸 서로 다른 `user_id` **2개**(한 사람이 기기·브라우저를 둘 쓰면 이렇게 잡힙니다). **제3자 데이터가 없습니다.**

### 그래서 §2 키 분리의 작업량이 이렇게 달라집니다

| | 원문을 남긴 채 키 분리 | **먼저 파기하고 키 분리** |
| --- | --- | --- |
| 재암호화 대상 | 봉투 **60개** (30행 × `raw_text` · `masked`) | **0개** |
| 읽기 겸용 코드(새 키 실패 시 옛 키 재시도) | 필요 → 나중에 걷어내기 | **불필요** |
| `sha256` 대조 검증 배치 | 필요 | 불필요 |

**「반나절 + 배치 + 겸용 코드 제거」가 「새 키로 새로 쓰기 시작」으로 줄어듭니다.**

> 참고: 봉투가 30개가 아니라 **60개**인 것은 `yourstory.js` 420-430 행에서 `raw_text` 와 `masked` **둘 다** `encryptJSON` 을 타기 때문입니다(05 §1-2 에서 말씀드린 건).

### 파기해도 파일럿 관측은 하나도 잃지 않습니다

스키마가 이미 갈라 놨습니다 — `ys_order_source`(원문)와 운영 기록이 별도 표입니다.

| 지운다 | 남는다 |
| --- | --- |
| `ys_order_source` 30행 | `ys_order` 31 · `ys_audit` **128** · `ys_ledger` |

**실패 분포·게이트 임계값·톤 오진율·원장 대조가 전부 남는 쪽에 있습니다.**

### 방법 — 기존 삭제 경로를 씁니다

**수동 `DELETE` SQL 을 쓰지 않기를 권합니다.** policy §3-4 삭제 경로가 「원문만 파기, 운영 기록 보존」을 이미 구현하고 있고 **동작이 검증됐습니다**(`YS-20260810-0001` 이 `status=deleted` 인데 `ys_order_source` 에 대응 행 없음 — 제가 `ys_order` 31 vs `ys_order_source` 30 으로 독립 확인). 수동 SQL 은 그 구분을 사람이 매번 다시 지켜야 합니다.

### 제안하는 순서

1. **`ys_cut` 평문 처리 방침 확정** (아래 4절) ← 이것부터
2. 기존 삭제 경로로 원문 30건 파기
3. `ys_order` · `ys_audit` · `ys_ledger` 보존 확인
4. **키 분리 착수** — 재암호화·겸용 코드 없이

**되돌릴 수 없으므로, 파일럿 분석에 원문이 더 필요하지 않은지 개발 세션이 먼저 확인해 주십시오.** 통상은 필요 없다고 봅니다만 판단은 그쪽이 낫습니다.

## 4. 확인 요청 3건

### 4-1. `ys_cut` 의 평문을 함께 지워야 합니까

`ys_cut.caption` · `dialogue` · `source_span` 에 **원문에서 따온 문장이 평문으로** 들어갑니다(`source_span` 은 정의상 원문 인용입니다). **원문을 파기하면서 이쪽을 남기면 파기가 반쪽이 됩니다.**

* 남긴다면 — 파기의 의미가 어디까지인지 정의가 필요합니다
* 함께 지운다면 — 컷 구조 관측(컷 수·재생성 횟수)이 얼마나 손실되는지 확인이 필요합니다

**정책 문서에 「판단 필요」로 표시해 뒀습니다. 개발 세션 의견을 청합니다.**

### 4-2. 사주 프로필 파기 경로가 없습니다

`suite_user.saju_profile` (생년월일시)에 **파기 경로가 구현돼 있지 않습니다.** 현재 채워진 것은 **55행 중 1건**뿐이라 급하지 않으나, **외부 참가자를 받기 전에는 있어야 합니다.**

### 4-3. G4 건수 재확인 (05 §2에서 물은 것)

`04` §5 표의 **G4 6건**이 제 실측 `fail_reason` 기준 **5건**과 어긋나고, 표의 합(10)이 실패 9건을 하나 넘습니다. **오기인지, `budget_stop` 1건을 G4 로 재분류하면서 두 칸에 겹쳐 센 것인지** 확인 부탁드립니다.
