## 1. §2 키 구조 — **사실입니다. 확인했습니다**

`src/lib/crypto.js` 실측:

| 파생 | 실제 코드 | 위치 |
| --- | --- | --- |
| 뿌리 | `secretOf(env) { return env.SESSION_SECRET; }` | 33-45행 |
| AES | `SHA-256(SESSION_SECRET + ":aes")` → AES-GCM 키 | 48-59행 |
| HMAC | `SESSION_SECRET + ":hmac"` → HMAC-SHA256 키 | 61-73행 |
| IP 해시 | `SHA-256(SESSION_SECRET + ":ip:" + ip)` | 137행 (04 문서는 135행 — **사소한 어긋남**) |

`user.js` 30-50행에서 쿠키 `mg_uid` 를 `verify()`·`sign()` 으로 처리하고, 그것이 위 HMAC 키를 씁니다. `yourstory.js` 420-430행에서 `encryptJSON(env, text)` · `encryptJSON(env, masked)` 로 고객 원문이 위 AES 키를 씁니다.

> **결론: `SESSION_SECRET` 하나에 쿠키 서명(게임+너의스토리) · IP 해시 · 고객 원문 암호화가 모두 매달려 있습니다. 개발 세션 주장 그대로입니다.**
>
> **양쪽 세션이 모두 못 봤던 것이 맞습니다.** 저는 어제 `wrangler.jsonc` 주석에서 시크릿 두 개(`SESSION_SECRET` · `YS_WORKER_SECRET`)를 보고 **분리돼 있다고 넘겨짚었습니다.** 후자는 워커 브리지 인증이고 암호화와 무관합니다.

### 1-1. 한 가지 표현을 더 정확히 합니다

04 문서 §2 에 *"파생은 도메인 분리(`:aes` / `:hmac`)가 되어 있어 그 자체는 올바릅니다"* 라고 쓰셨습니다. 맞습니다. 다만 **그 문장이 위험을 축소해 읽힐 수 있습니다.**

도메인 분리는 **한쪽 용도의 서명을 다른 쪽으로 재사용하는 것**을 막습니다. 그러나 **`SESSION_SECRET` 자체가 새면 세 가지가 동시에 무너집니다** — `:aes` 도 `:hmac` 도 `:ip:` 도 그 값에서 결정론적으로 계산됩니다. 그리고 **HMAC 키는 해시를 거치지 않고 `secret + ":hmac"` 를 그대로 키로 씁니다**(61-73행). 기능상 문제는 없지만(HMAC 은 임의 길이 키 허용), **AES 쪽만 SHA-256 을 거치는 비대칭**이라 키 파생을 정리할 때 함께 보시길 권합니다.

**「파생이 올바른 것」과 「근본 키가 갈린 것」은 다릅니다.** §2 의 권고 1(`YS_ENC_SECRET` 신설)이 필요한 이유가 정확히 이것입니다.

### 1-2. 보탬 셋

1. **재암호화 시 `sha256` 칼럼을 무결성 검증에 씁니다.** `ys_order_source.sha256` 은 원문 해시입니다(0021 주석: *"창작기록서는 원문 대신 이 해시를 인용한다"*). 배치 재암호화를 **복호 → `sha256` 대조 → 재암호** 순으로 하면 **조용한 손상을 그 자리에서 잡습니다.** 검증 수단이 이미 스키마에 있습니다.

2. **암호문은 30개가 아니라 60개입니다.** `ys_order_source` 는 `raw_text` 와 `masked` **둘 다** 봉투입니다(420-430행에서 `encryptJSON` 두 번). 30행 × 2 = **60개.** 규모는 여전히 작지만 재암호화 스크립트가 둘 다 처리해야 합니다.

3. **스테이징 키는 이미 갈려 있습니다.** `wrangler.jsonc` 에 `wrangler versions secret put SESSION_SECRET --env staging` 이 별도로 있습니다 — 좋은 격리입니다. 다만 §3-3 의 검사 6번(암·복호 왕복)을 로컬에서 돌리려면 **로컬 `SESSION_SECRET`(`.dev.vars`)이 필요**하다는 점을 테스트 문서에 적어 두시길 권합니다.

## 2. §5 실패 분포 — **이견 1건 (G4 6건 vs 5건)**

프로덕션 D1 을 `fail_reason` 까지 조회했습니다. 8/12~8/13 주문 **10건 전량**입니다.

**단정하지 않겠습니다** — 두 가지 가능성이 있습니다.

1. **오기.** G4 는 5건이고 합은 9건이 맞다.
2. **재분류.** `budget_stop`(0812-0002)의 실제 원인이 **재생성 반복 = G4** 라서 G4 로 세고, 「예산 중단」 칸에도 남겨 **한 건이 두 번 세어졌다.** §5 결론의 *"여섯 번을 예산 부족으로 읽었는데 실제 원인은 1건뿐"* 과 맞물리는 해석입니다.

**어느 쪽인지 확인을 청합니다.** 사소해 보이지만 **이 분포가 「구조 문제 3 / 코드 결함 5 / 튜닝 1」 판정의 근거**이고, 그 판정이 다음 착수 순서를 정합니다.

### 검증하지 못한 것

**원장 대조는 보류합니다.** 제 쿼리가 `ys_ledger` 를 **기간 제한 없이** 집계해(consume 21 · refund 9 · grant 6, 전체 기간) 04 문서의 「8/12~13 실패 9건 중 과금 6건」과 **기간이 맞지 않습니다.** 같은 창으로 다시 재기 전에는 일치·불일치를 말하지 않겠습니다.

`ys-worker.js:275-290` 의 **멱등 처리는 코드로 확인했습니다** — `SELECT COUNT(*) ... reason='consume'` 로 이중 차감을 막고, 주석도 *"두 번 빠지는 것보다 한 번도 안 빠지는 편이 낫다"* 로 의도가 명시돼 있습니다. §3-3 의 검사 4번(멱등) 추가에 **동의합니다.**

## 3. §4 우선순위 — 조건에 동의합니다. 다만 **기준을 정확히 합니다**

「연속 2회 성공 후 D1 분리」에 **동의합니다.** 아홉 번 중 여섯 번을 엉뚱한 곳(예산)을 고치며 보냈다는 서술이 그 조건의 근거로 충분합니다.

**다만 04 문서의 논리에 비일관이 하나 있습니다.**

> §2 키 분리 = **2순위(지금)** / D1 분리 = **5순위(연속 성공 후)**

그런데 **둘 다 저장 계층**입니다. 실패 9건은 전부 G2·G4·예산 — **파이프라인**이고 저장이 아닙니다. 「새 변수를 넣으면 원인을 못 가른다」를 기준으로 삼으면 **키 분리도 같은 이유로 미뤄야** 합니다.

**진짜 기준은 「새 변수인가」가 아니라 「롤백이 되는가」로 보입니다.**

| | 실패 시 |
| --- | --- |
| 키 분리 | 시크릿 하나 추가 + 읽기 겸용. **되돌리기 쉽다** |
| D1 분리 | 바인딩 교체. 어긋나면 **너의스토리 전 기능 정지** |

이렇게 적으면 순위가 그대로면서 근거가 정확해집니다. **순위를 바꾸자는 것이 아니라 기준을 바꾸자는 것입니다** — 다음에 비슷한 판단을 할 때 같은 잣대를 쓸 수 있게.

## 4. §2 가 사실이면 **Q2 의 무게가 더 커집니다**

04 문서 §2 에 *"「키를 교체할 수 없는 시스템」은 보안 심사에서 지적 항목입니다"* 라고 쓰셨습니다. **개발 관점의 사실 진술로 받아들입니다**(저도 심사 판단은 하지 않습니다).

다만 그 사실이 우선순위에 주는 함의를 적어 둡니다.

* 금융사 심사에서 **정기 키 교체**는 흔한 요구입니다.
* 지금 구조에서는 **키를 바꾸면 고객 일기가 전부 복호화 불가**가 됩니다.
* 즉 **키 분리(§2)는 Q2 의 선행 조건**이기도 합니다 — 「가르라면 얼마나 걸리는가」의 답에 **반나절(D1) + 키 분리**가 들어가야 정확합니다.

**법무 질의서에 넣을 항목이 하나 늘었습니다** — 도메인 분리(제 03 §3-2)에 더해 **「현재 암호화 키가 세션 키와 공용이며 교체 시 기존 데이터 복호화 불가」** 를 사실로 기재해야, 법무가 실제 상태를 보고 판단합니다.
