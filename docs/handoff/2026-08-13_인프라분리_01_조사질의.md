# 개발 세션 확인 요청 — 너의스토리와 미니게임의 인프라 분리 (2026-08-13)

> 작성: 조사 세션 · 요청: Master

## 0. 먼저 — 걱정하신 것 중 절반은 이미 되어 있습니다

Master 질문: *"yourstory가 DB에 생성됐다는데 문제 소지는 없나? 미니게임 영역과 분리해서 관리해야 하는 것 아닌가?"*

**스키마는 이미 깨끗하게 분리돼 있습니다.**

| 확인 항목 | 실측 결과 |
| --- | --- |
| 마이그레이션 `0021`·`0022`·`0023` 이 기존 게임 테이블을 건드리는가 | **아니오.** 전부 `ys_` 접두 **신규 8개 테이블**(`ys_invite`·`ys_order`·`ys_order_source`·`ys_cut`·`ys_episode`·`ys_ledger`·`ys_worker`·`ys_audit`) 생성 + `ys_worker` 에 컬럼 3개 추가뿐 |
| 기존 테이블 `ALTER`·`DROP` | **0건** |
| R2 저장소 | **이미 분리** — 웹툰 `webtoon-assets` / 너의스토리 `yourstory-assets` **별도 버킷**. 분리 이유가 주석에 적혀 있음(연재분은 전원 공개·1년 캐시, 너의스토리는 비공개 — 같은 버킷이면 캐시 규칙 한 줄 실수로 남의 이야기가 공개된다) |
| 스테이징 | **이미 분리** — 별도 Worker(`minigames-staging`) + **별도 D1**(`minigames-staging-db`) + 별도 버킷 |
| 고객 원문 보호 | 원문·마스킹본 **AES-256-GCM 암호화 저장**, 민감정보(의료·종교·성적지향·정치성향) 플래그, 삭제 시 원문만 파기하고 운영 기록은 남기는 표 분리 설계 |

**설계자가 이미 신중하게 갈라 놓았습니다.** 아래 질문들은 「분리를 안 했다」가 아니라 **「어디까지 갈랐고, 안 가른 곳은 의도인가」** 를 확인하는 것입니다.

## 1. 실측 사실 (질문의 근거)

### 1-1. Cloudflare 계정 조회 (2026-08-13)

| 항목 | 값 |
| --- | --- |
| Worker | **`minigames`** (프로덕션, 생성 2026-07-25) / `minigames-staging` (2026-08-03) — **2개** |
| `minigames` 마지막 배포 | **2026-08-13 02:50:53Z** ← 어젯밤 너의스토리 코드가 **실제로 배포됐습니다** |
| D1 `minigames-db` | 테이블 **39개** · 용량 **753,664 B (약 0.75 MB)** · 리전 APAC · **읽기 복제 비활성** |
| D1 용량 여유 | 10 GB 상한 대비 **0.0074%** — **용량은 당분간 걱정거리가 아닙니다** |

### 1-2. 한 Worker 안에서 공유되는 것

`wrangler.jsonc` 실측:

```
"run_worker_first": ["/game/*", "/ad/*", "/user/*", "/api/*", "/webtoon/w/*", "/ys/*"]
"d1_databases":     [ DB → minigames-db ]          ← 게임과 너의스토리가 같은 DB
"triggers": { "crons": ["*/10 * * * *", "* * * * *"] }   ← cron 2개
```

* **배포 단위가 하나**입니다. `src/index.js` 하나가 게임·타로·사주·심리·웹툰·너의스토리를 전부 라우팅합니다.
* 너의스토리 코드는 **1,291줄**(`yourstory.js` 568 + `ys-worker.js` 607 + `ys-alert.js` 116)이고, 진입점 `index.js` 는 394줄입니다.
* **cron 이 2개**입니다. `*/10` 은 세션 청소(원래 있던 것), **`* * * * *` 는 너의스토리 워커 감시로 새로 붙었습니다 — 하루 1,440회 추가 실행**입니다. `index.js` 283~286 에서 `event.cron` 으로 갈라 청소를 매분 돌리지 않게 막아 둔 것은 확인했습니다.
* **`YS_WORKER_SECRET`** 이 이 Worker 의 시크릿으로 들어갑니다. 주석에 *"이 값이 새면 남이 대기열을 집어가 고객의 원문을 읽을 수 있다"* 고 적혀 있습니다.

### 1-3. 좋은 신호 하나

어젯밤 **02:50 에 너의스토리 코드가 배포됐고, 오늘 아침 배포본을 확인하니 게임 30종이 정상**이었습니다(`sync_deployed_games.py` 30종과 일치). **이번 배포는 게임을 깨지 않았습니다.**

## 2. 확인 요청 — 6건

### Q1. 【최우선】 배포 단위를 왜 하나로 두는가 — Worker 를 가를 계획이 있는가

**무엇이 걸리는가**: 지금은 **너의스토리 코드 한 줄의 오류가 미니게임 30종을 같이 죽입니다.** 스키마는 갈랐는데 **실패 반경(blast radius)은 안 갈렸습니다.** 배포도 `main` push 자동이라, 너의스토리만 고쳐 push 해도 게임이 함께 새 버전으로 나갑니다.

**묻는 것**
1. 한 Worker 를 유지하는 것이 **의도된 선택**입니까? (정적 자산·세션 쿠키·`/api/*` 공유 때문이라면 납득됩니다)
2. 가른다면 어느 선입니까 — ① Worker 분리(`minigames` / `yourstory`) ② Service Binding 으로 호출만 분리 ③ 지금 유지
4. 지금 유지라면, **너의스토리 경로에서 던진 예외가 게임 경로로 새지 않는다**는 것이 코드로 보장됩니까? (`/ys/*` 핸들러 전체가 try/catch 로 감싸여 있는지)

> **조사 세션 의견**: 지금 당장 가르라는 뜻이 아닙니다. 너의스토리는 **0단계 내부 파일럿**(초대코드 20건)이라 트래픽이 거의 없습니다. 다만 **파일럿이 끝나고 외부 공개로 갈 때가 분리의 마지막 시점**이라고 봅니다.

---

### Q2. 【최우선】 금융사 제휴 심사에서 같은 DB·같은 도메인이 문제가 되지 않는가

**무엇이 걸리는가**: 이 프로젝트의 제휴 대상은 **OK캐쉬백·하나머니·KB국민카드·해피포인트·L.POINT·시럽·트래블로그·신한카드** 입니다. 그런데 같은 Worker·같은 D1·같은 도메인에 **고객이 직접 쓴 개인 일기**가 쌓이고, 스키마에는 **민감정보 플래그(의료·종교·성적지향·정치성향)** 가 있습니다.

**금융사 보안·개인정보 심사에서 「같은 처리 시스템에 무엇이 함께 있는가」는 반드시 묻는 항목**입니다. 미니게임만 보면 수집 정보가 거의 없는데, 같은 DB 안에 민감정보가 있으면 심사 범위가 통째로 넓어집니다.

**묻는 것**
1. 제휴 제안 시 **미니게임만 별도 시스템으로 제시할 수 있는 구성**입니까?
2. 개인정보 처리방침·처리 위탁 범위에서 두 서비스가 **분리 기재**됩니까?
3. 분리가 필요하다면 **D1 을 갈라야 하는가**(`yourstory-db` 신설), 아니면 논리적 분리 + 접근통제 문서로 충분한가?

> **저는 법률·심사 판단을 할 수 없습니다.** 이 항목은 「개발이 답할 것」이 아니라 **Master가 법무·제휴 담당과 확인하실 것**으로 올립니다. 개발에는 **「가르라면 얼마나 걸리는가」** 만 물으면 됩니다.

---

### Q3. cron 매분 실행 — 비용과 한도를 확인했는가

**실측**: `triggers.crons` 에 `* * * * *` 가 추가돼 **하루 1,440회** 스케줄 실행이 생겼습니다. 청소(`*/10`)와 갈라 둔 것은 확인했습니다.

**묻는 것**
1. 매분 실행이 Workers 요청 한도·과금에 미치는 영향을 **계산해 보셨습니까?** (계정 플랜을 제가 모르므로 수치를 만들지 않습니다)
2. 워커 감시가 **매분이어야 하는 근거**는 무엇입니까? 주석에 *"그 간격이 곧 탐지 지연"* 이라고 적혀 있는데, **5분이면 안 되는 이유**가 파일럿 단계에서도 성립합니까?
3. `ys_worker` heartbeat 갱신이 **D1 쓰기**입니다. 매분 감시 + 워커의 잦은 갱신이 D1 일일 쓰기 한도에 어떻게 잡힙니까?

---

### Q4. 너의스토리가 게임의 공통 자원을 건드리는가

**확인하지 못한 것**입니다 — 코드를 다 읽지 않았습니다.

**묻는 것**
1. 너의스토리가 게임과 **같은 `user_id`(서명 쿠키 `mg_uid`)** 를 씁니다. 한쪽에서 쿠키 정책·서명 방식을 바꾸면 **다른 쪽 사용자 식별이 깨집니까?**
2. `src/lib/` 공용 모듈(`crypto.js`·`user.js`·`http.js`·`db.js`)을 양쪽이 공유합니다. **너의스토리 때문에 공용 모듈을 고칠 때 게임 회귀 테스트가 도는 구조**입니까?
3. `sessions` 테이블 청소(`cleanupSessions`)가 너의스토리 주문 상태에 영향을 줍니까? (주문은 별도 표라 없을 것으로 보이나 확인 요청)

---

### Q5. 백업·복구 단위가 하나인데 괜찮은가

**무엇이 걸리는가**: D1 이 하나라 **백업·시점 복구(PITR)도 하나**입니다. 너의스토리 사고로 DB 를 과거 시점으로 되돌리면 **게임 기록도 같이 되돌아갑니다.** 반대도 마찬가지입니다.

**묻는 것**
1. `minigames-db` 의 **백업 주기와 복구 절차**가 정해져 있습니까?
2. 한쪽만 되돌려야 하는 상황의 **절차가 있습니까?** (예: `ys_*` 테이블만 별도 export)
3. **읽기 복제가 비활성**입니다(실측). 파일럿 중엔 무관하나, 외부 공개 시 켤 계획입니까?

---

### Q6. 스테이징에서 너의스토리를 먼저 도는가

**실측**: 스테이징은 별도 Worker + 별도 D1 + 별도 버킷으로 **잘 갈라져 있습니다.** 다만 `minigames-staging` 의 마지막 수정이 **2026-08-04** 이고, 프로덕션은 **08-13** 입니다. **9일 벌어져 있습니다.**

**묻는 것**
1. 너의스토리 0021~0023 마이그레이션이 **스테이징 D1 에도 적용됐습니까?**
2. 프로덕션에 먼저 나가고 스테이징이 뒤따르는 순서라면, **스테이징의 역할이 무엇입니까?**
3. `d1 migrations apply --remote` 는 되돌릴 수 없습니다. **프로덕션 적용 전에 스테이징에서 먼저 도는 규칙**이 있습니까?

## 3. 조사 세션이 매일 지켜보기로 한 것

Master 지시로 **「미니게임 배포본 일일 점검 (운영)」** 예약 작업을 만들었습니다(평일 09:30, `trig_0154LSFFMT2TzfJjBMB4ohcz`). **이상이 있는 날에만** 알립니다.

| 점검 | 이 문서와의 관계 |
| --- | --- |
| 배포본 응답 + 게임 30종 | **Q1 의 위험을 그날 안에 잡는 장치** |
| `wrangler.jsonc`·`src/index.js`·`src/lib/config.js` 변경 | Q1·Q4 |
| `migrations/` 새 파일 | **Q6 — `--remote` 는 비가역** |
| `sync_deployed_games.py` 일치 | 대조군 |

**스모크 테스트(`npm run test:api`·`test:abuse`)는 점검에서 뺐습니다** — `BASE` 가 `http://127.0.0.1:8787`(로컬 `wrangler dev`)이라 클라우드 세션에서 Master 기기의 localhost 에 닿을 수 없습니다. **배포 직전 실행은 개발 세션 몫입니다.**

> `test-api.mjs` 의 **「PLAYERS 에 등록 안 한 게임은 실패시킨다」** 장치는 테스트 없이 게임이 들어가는 것을 막는 좋은 안전망입니다. **그대로 두시길 권합니다.**

## 5. 조사 세션이 하지 않은 것 (명시)

* `minigames` 저장소를 **읽기만** 했습니다. 파일 수정·`git` 실행 없음.
* `.dev.vars` 등 **시크릿 파일은 열지 않았습니다.**
* Cloudflare 계정은 **조회만** 했습니다(Worker 목록·D1 정보). 변경 없음.
* **계정 플랜·과금 수치는 확인하지 못해 만들지 않았습니다** — Q3 은 「계산해 보셨는가」를 묻는 것이지 제가 계산한 값을 제시하는 것이 아닙니다.
* **법률·개인정보 심사 판단은 하지 않았습니다.** Q2 는 확인 요청이지 결론이 아닙니다.
