## 1. Q1 — 배포 단위

### 1-1. 예외 격리는 코드로 보장됩니다

물으신 3번에 답합니다. `src/index.js` 를 읽었습니다.

* **모든 라우트가 단일 `try/catch` 안에 있습니다** (`index.js:367-392`). `/ys/*` 도 예외가 아닙니다.
  `ApiError` 는 그 상태코드로, 그 외 예외는 로그만 남기고 `500 INTERNAL` 로 떨어집니다.
* `/ys/w/asset` 은 본문이 이미지 바이트라 공통 경로를 안 타는데, **거기에도 별도 `try/catch` 가 있습니다** (`index.js:348-354`).
* Workers 는 **요청마다 격리된 isolate** 입니다. 한 요청의 런타임 예외가 다른 요청으로 새지 않습니다.

**→ 너의스토리 핸들러가 던진 런타임 예외로 게임이 죽지 않습니다.**

### 1-2. 다만 진짜 공유 위험은 그쪽이 아닙니다

`try/catch` 로 막을 수 없는 것이 하나 있습니다 — **모듈 로드 단계의 실패**입니다.
`import` 오류, 문법 오류, `config.js` 의 최상위 예외는 **Worker 자체가 안 뜹니다.** 그러면 게임 30종이 함께 죽고, 위의 `try/catch` 는 실행될 기회조차 없습니다.

**이것은 가상의 이야기가 아닙니다.** 오늘(08-13) 너의스토리 이미지 원가 때문에 `src/lib/config.js` 를 **두 번** 고쳐 push 했습니다(630→741→798원). 그 파일은 게임 30종의 상수도 들고 있습니다. 상수 한 줄이라 안전했지만, **같은 파일을 고쳐 같은 배포로 내보냈다는 사실은 그대로입니다.**

정리하면 — 조사 세션이 걱정한 「코드 한 줄의 오류」는 **런타임 예외라면 이미 막혀 있고, 로드 단계 오류라면 못 막습니다.** 후자가 진짜 실패 반경입니다.

### 1-3. 답변

1. **의도된 선택입니다.** 정적 자산·세션 쿠키(`mg_uid`)·`/api/*` 를 공유하고, `wrangler.jsonc` 의 `run_worker_first` 에 `/ys/*` 가 함께 들어가 있습니다. 지금 가르면 쿠키 서명키와 정적 자산 경로를 먼저 갈라야 합니다.
2. **분리 시점 의견은 조사 세션과 같습니다** — 파일럿 종료 후 외부 공개 직전. 지금은 트래픽이 사실상 0이라(게임 `sessions` 표가 **0행**, `results` 누계 **63행**) 분리의 이득이 비용보다 작습니다.
3. 가른다면 **① Worker 분리**를 권합니다. Service Binding(②)은 배포 단위를 못 가르므로 이 문제(로드 단계 실패)를 해결하지 못합니다.

## 2. Q2 — 금융사 심사

**법률·심사 판단은 하지 않습니다.** 조사 세션 판단에 동의하며, 개발에 물으신 「가르라면 얼마나 걸리는가」에만 답합니다.

### D1 분리 (`yourstory-db` 신설) — **반나절**

* 마이그레이션 `0021`·`0022`·`0023` 을 새 DB 에 적용 (파일 그대로 재사용).
* `wrangler.jsonc` 에 두 번째 D1 바인딩 추가, 너의스토리 코드에서 `env.DB` → `env.YS_DB`.
* 손댈 파일은 **3개뿐**입니다 — `services/yourstory.js` · `routes/ys-worker.js` · `services/ys-alert.js`.
* 데이터 이관 **31행**(`ys_order` 기준). 전체 DB 가 0.75 MB 라 초 단위입니다.

**교차점이 딱 하나 있습니다.** `yourstory.js:38` 이 `lib/suite.js` 의 `touchUser()` 를 부릅니다 — **게임과 같은 사용자 표에 씁니다.** DB 를 가르면 이 한 줄을 어떻게 할지 정해야 합니다(빼거나, 양쪽에 쓰거나). 그 외에 너의스토리가 게임 표를 만지는 곳은 없습니다.

### Worker 분리 — **2~3일**

라우팅·정적 자산·쿠키 서명키 공유를 끊어야 해서 D1 분리보다 훨씬 큽니다.

### 심사에 쓸 수 있는 사실 하나

**삭제 경로가 실제로 동작합니다.** `YS-20260810-0001` 이 `status=deleted` 인데 `ys_order_source` 에 대응 행이 **없습니다** — 설계대로 원문만 파기되고 운영 기록은 남았습니다. 설계 문서가 아니라 **데이터로 증명됩니다.**

## 3. Q3 — cron 매분

### 3-1. 실측 산수

| 항목 | 주기 | 하루 | D1 |
| --- | --- | --- | --- |
| cron `* * * * *` (워커 감시) | 1분 | **1,440회** | `ys_worker` 1행 SELECT. 상태가 바뀔 때만 UPDATE |
| cron `*/10` (세션 청소 외) | 10분 | 144회 | 기존 부하 |
| **PC 브리지 폴링** | **20초** | **4,320회** | 요청마다 ① 유실회수 UPDATE ② `beat()` UPSERT = **쓰기 2회** |

* **Worker 요청 합계 ≈ 5,760회/일**
* **D1 쓰기 ≈ 8,640행/일** (브리지가 대부분, cron 은 거의 0)

무료 플랜 기준(요청 100,000/일 · D1 쓰기 100,000행/일 · 읽기 5,000,000/일)으로 **요청 5.8% · 쓰기 8.6%** 입니다.

### 3-2. 답변

1. **계산했고, 지금 규모에선 문제가 없습니다.** 다만 계정 플랜은 제가 확인하지 못했습니다(미확인).
2. **매분이어야 할 근거는 약합니다.** 접수 차단 기준이 `WORKER_STALE_MS = 5분` 인데 감시가 5분 주기면 최악 10분까지 늦습니다 — 그래서 매분으로 둔 것은 논리적입니다. 다만 초대 20건 파일럿에서 5분과 10분의 차이는 실익이 작습니다. **줄여도 되지만, 비용이 문제가 아니므로 급하지 않습니다.**
3. **정정 하나** — 조사 세션이 cron 을 부하의 주범으로 보셨는데, **실제 D1 쓰기는 브리지 폴링이 압도적입니다**(cron 의 3배). 그리고 이 부하는 **주문이 0건이어도 24시간 일정합니다.** 줄이시려면 cron 보다 `POLL_SEC = 20` (`ys_bridge.py:45`) 쪽이 효과가 큽니다.

## 4. Q4 — 공통 자원

1. **같은 쿠키(`mg_uid`)를 씁니다.** 서명 방식을 바꾸면 양쪽 사용자 식별이 함께 깨집니다.
   다만 **너의스토리 쪽이 오히려 안전합니다** — 진짜 신원이 초대코드라, 쿠키가 날아가도 코드를 다시 넣으면 지난 주문까지 따라옵니다(`yourstory.js` 의 `invite` 핸들러가 `ys_order.user_id` 를 함께 옮깁니다). **게임에는 그런 복구 수단이 없습니다.**

2. **🔴 회귀 테스트가 한 방향뿐입니다.** 이것이 Q4 에서 가장 실질적인 위험입니다.
   양쪽이 `lib/` 의 `crypto.js` · `http.js` · `config.js` · `time.js` · `suite.js` 를 공유하는데, **`scripts/test-api.mjs` 에 너의스토리 시나리오가 0개입니다**(문자열 검색 8건은 전부 `Object.keys`·`.status` 오탐이었습니다).

   > 너의스토리 때문에 공용 모듈을 고치면 → 게임 테스트가 잡습니다.
   > **게임 때문에 공용 모듈을 고치면 → 너의스토리가 깨져도 아무도 못 잡습니다.**

   조사 세션이 칭찬한 「PLAYERS 에 등록 안 한 게임은 실패시킨다」 장치의 **너의스토리판이 없는 셈**입니다.

3. **`cleanupSessions` 는 무관합니다.** `lib/db.js:303` 에서 `DELETE FROM sessions` 만 합니다. `ys_*` 를 건드리지 않습니다. 확인했습니다.

## 5. Q5 — 백업·복구

1. **정해진 백업 주기도 복구 절차도 없습니다.** 문서에도 코드에도 없습니다.
2. D1 Time Travel 은 **DB 단위**라 표 단위 복구가 없습니다 — 조사 세션 지적이 정확합니다.
3. **다만 지금은 쉽게 해결됩니다.** 전체 DB 가 **0.75 MB**(ys 관련 337행 + 게임 63행)입니다.
   `wrangler d1 export` 덤프를 하루 한 번 남기면 **표 단위 복구가 가능해집니다** — Time Travel 을 기다릴 필요가 없습니다. 지금 규모에선 몇 초입니다.
4. **읽기 복제는 지금 켤 이유가 없습니다.** 쓰기 지연만 늘고 트래픽이 없습니다. 외부 공개 시 재검토.

## 6. Q6 — 스테이징 🔴

**조사 세션의 추정보다 나쁩니다.**

스테이징 D1(`minigames-staging-db`)을 직접 조회했습니다:

```sql
SELECT name FROM sqlite_master WHERE type='table' AND name LIKE 'ys_%';
-- → 0건
```

* **마이그레이션 `0021`·`0022`·`0023` 이 스테이징에 적용된 적이 없습니다.**
* 즉 **너의스토리는 스테이징에서 한 번도 돈 적이 없습니다.** 프로덕션이 첫 실행 환경입니다.
* 게다가 `wrangler.jsonc` 의 staging 환경은 **`"crons": []`** 라 워커 감시 자체가 없습니다(프로덕션에서만 돕니다). 스테이징에서 돌리려 해도 대기열이 안 돕니다.

### 답변

1. **아니오, 적용되지 않았습니다.**
2. **현재 스테이징은 게임 전용입니다.** 너의스토리에 관한 한 역할이 없습니다.
3. **그런 규칙이 없습니다.** `--remote` 는 되돌릴 수 없는데 대조군 없이 프로덕션에 바로 적용해 왔습니다.

### 권고 (개발 세션 의견)

* **규칙을 세웁니다** — 마이그레이션은 스테이징 먼저, 확인 후 프로덕션.
* **지금 `0021~0023` 을 스테이징에 적용해 둡니다.** 다음 마이그레이션 때 비교할 대조군이 생깁니다. 지금은 표가 없어서 「스테이징에서 먼저 돌린다」가 물리적으로 불가능합니다.
* 스테이징에서 대기열까지 돌리시려면 `crons` 를 살려야 합니다.

## 7. 조사 세션이 보지 못한 것 (추가 발견)

### 7-1. 일일 상한 쿼리가 인덱스를 못 탑니다

`services/yourstory.js` 의 `committed()`:

```sql
FROM ys_order WHERE id LIKE ? OR status IN (...)
```

`LIKE` 와 `OR` 조합이라 **풀스캔**입니다. 그런데 이 함수는 **주문 접수마다** 호출됩니다.

31행인 지금은 무관하지만, 외부 공개로 주문이 쌓이면 접수 응답이 선형으로 느려집니다. `created_at` 범위 조건으로 바꾸면 인덱스를 탑니다. **지금 고칠 일은 아니고, 공개 전 체크리스트 항목입니다.**

### 7-2. 인덱스 설계는 좋습니다

확인 결과 필요한 자리에 정확히 있습니다.

| 인덱스 | 쓰는 쿼리 |
| --- | --- |
| `idx_ys_order_queue (status, created_at)` | 워커 `claim` — 가장 오래 기다린 한 건 |
| `idx_ys_order_mine (user_id, created_at DESC)` | 고객 서랍 목록 |
| `idx_ys_ledger_code (invite_code, at DESC)` | 잔액 집계 |

`ys_worker` 에 인덱스가 0개인 것은 **정상**입니다 — `id INTEGER PRIMARY KEY CHECK (id = 1)` 인 단일 행 표라 rowid 로 직접 찾습니다.

### 7-3. 잔액을 원장 합계로 읽는 설계가 오늘 실제로 값을 했습니다

오늘 파일럿 10회 중 8회가 실패했는데, **환불이 전부 원장에 남아 대조가 가능했습니다**(`consume` → `refund` 쌍). 스칼라 칼럼만 있었으면 「왜 이 숫자인가」를 되짚을 수 없었을 것입니다. `ys_invite.tickets` 를 사본으로만 쓴 판단이 옳았습니다.
