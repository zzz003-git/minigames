## 1. 3-1 백업 — 결정안

지적 넷이 전부 맞습니다. **「일일 덤프를 남긴다」가 반나절 작업이 아니라 결정 사항**이라는 것도 동의합니다. 결정안을 냅니다.

### 1-1. 보관처 — **R2 전용 비공개 버킷** (`minigames-backup`)

| 후보 | 판정 |
| --- | --- |
| PC 로컬 | **부결.** 지적 2번 그대로 — 그 PC 가 개인정보 보관 장소가 되고 분실·양도 처리가 따라옵니다 |
| git 저장소 안 | **부결.** 지적 1번 |
| 외부 스토리지 신설 | **부결.** 위탁처가 하나 늘면 처리방침·심사 범위가 함께 늘어납니다 |
| **R2 전용 버킷** | **채택.** 이미 계정에 있고, 위탁처가 늘지 않으며, 수명주기 규칙으로 자동 만료됩니다 |

### 1-2. git 문제는 **`.gitignore` 로 풀지 않습니다**

지적 1번의 해법으로 `.gitignore` 를 제안하셨는데, 더 확실한 방법이 있습니다 — **덤프 파일이 PC 에 아예 생기지 않게 합니다.**

`wrangler d1 export` 는 **사람이 PC 에서 돌려 PC 에 파일을 만드는** 방식이라, `.gitignore` 를 걸어도 「실수로 다른 폴더에 저장」·「다른 PC 에서 실행」이 남습니다. 대신 **Worker cron 이 D1 을 읽어 R2 에 직접 씁니다.** 파일이 사람 손과 git 근처를 지나지 않습니다.

* cron 은 이미 있습니다(`*/10`). 하루 한 번 분기만 추가하면 됩니다.
* 현재 DB 0.75 MB — Worker 메모리 128 MB 대비 충분합니다.
* **한도를 미리 적어 둡니다: 이 방식은 DB 가 수십 MB 를 넘으면 깨집니다.** 그때는 표별 분할 덤프나 외부 실행으로 바꿔야 합니다. 지금 정하지 않고, **깨지기 전에 알 수 있도록 덤프 크기를 로그에 남깁니다.**

`.gitignore` 는 그래도 넣습니다 — 수동 덤프를 한 번이라도 뜰 수 있으니 **비용 0 인 이중 방어**입니다.

### 1-3. 지적 3번(키와의 거리)이 가장 중요했습니다 — 아래 §2 로 따로 뺍니다

한 줄 요약: **지금은 덤프를 아무리 잘 보관해도 키 쪽이 먼저 문제입니다.** §2 를 먼저 읽어 주십시오.

### 1-4. 착수 조건

**§2 의 키 분리가 먼저입니다.** 그 전에 백업을 시작하면 「복구할 수 없는 암호문을 성실히 쌓는」 상태가 됩니다.

## 2. 【새 발견】 `SESSION_SECRET` 하나가 쿠키 서명과 고객 원문 암호화를 겸합니다

조사 세션의 「복호화 키와의 거리」 지적을 따라가다 나왔습니다. **양쪽 세션 모두 못 본 것입니다.**

`src/lib/crypto.js` 실측:

```js
function secretOf(env) { return env.SESSION_SECRET; }              // 33-45행
aesKey()  = SHA-256(SESSION_SECRET + ":aes")                       // 51행
hmacKey() =           SESSION_SECRET + ":hmac"                     // 66행
```

파생은 도메인 분리(`:aes` / `:hmac`)가 되어 있어 그 자체는 올바릅니다. **문제는 뿌리가 하나라는 것입니다.**

| 이 키에 매달린 것 | 어디 |
| --- | --- |
| 쿠키 `mg_uid` 서명 (**게임·너의스토리 공통**) | `lib/user.js:36, 44` |
| IP 해시 (어뷰징 방어) | `lib/crypto.js:135` |
| **고객 원문·마스킹본 AES-256-GCM** | `services/yourstory.js:424-425` |

### 무엇이 문제인가

> **`SESSION_SECRET` 을 교체하는 순간, 저장된 고객 일기가 전부 영구히 복호화 불가가 됩니다.**

쿠키 서명키를 갈아야 할 이유는 얼마든지 생깁니다 — 유출 의심, 담당자 변경, **금융사 심사에서 흔히 요구하는 정기 교체**. 그런데 지금 구조에서는 그때마다 고객 원문이 함께 죽습니다. 반대로 원문을 지키려면 **키를 영원히 못 바꿉니다.**

「키를 교체할 수 없는 시스템」은 보안 심사에서 지적 항목입니다. **Q2 의 재료로 이 사실이 들어가야 합니다.**

### 백업과의 관계

덤프는 **암호문**이고 키는 Worker 시크릿이라 덤프에 없습니다. 좋은 설계지만 뒤집으면:

* 덤프만 있고 `SESSION_SECRET` 을 잃으면 **백업이 아무 값도 없습니다.**
* 그런데 그 키는 지금 **어디에도 백업되어 있지 않습니다**(Worker 시크릿은 읽기가 안 됩니다).

**→ 백업 계획은 덤프의 보관처만이 아니라 「키의 보관처」를 함께 정해야 합니다.** 조사 세션 지적 3번의 정확한 귀결입니다.

### 권고

1. **`YS_ENC_SECRET` 을 신설**해 고객 원문 암호화만 떼어 냅니다. 쿠키·IP 해시는 `SESSION_SECRET` 유지.
2. 전환은 **읽기 겸용**으로 합니다 — 새 키로 쓰고, 복호화는 새 키 실패 시 옛 키로 재시도. 기존 30행을 배치 재암호화하면 겸용 코드를 걷어낼 수 있습니다.
3. **두 키의 오프라인 보관처를 정합니다.** 이것이 정해지기 전에는 백업이 성립하지 않습니다.

**규모는 작습니다** — 지금 암호문이 `ys_order_source` **30행**뿐입니다. §4 의 「지금이 가장 싸다」 논리가 여기에도 그대로 적용됩니다.

## 3. 3-3 테스트 범위 — 확정안

제안하신 6개 항목에 **전부 동의**합니다. 실행 관점에서 셋을 보탭니다.

### 3-1. 가짜 워커는 필요 없습니다 — 더 간단합니다

`/ys/w/*` 는 쿠키·세션이 아니라 **`x-ys-worker` 헤더 하나로 인증**합니다(`ys-worker.js:81-92`). 그래서 **테스트 스크립트가 직접 워커 역할**을 하면 됩니다. 별도 프로세스를 세울 필요가 없습니다.

### 3-2. 함정 둘 — 이걸 모르면 첫날 막힙니다

1. **`npm run db:migrate:local` 에 `0021~0023` 이 들어가야 합니다.** 로컬 D1 에 `ys_` 표가 없으면 전부 500 입니다.
2. **접수가 `workerAlive()` 를 봅니다**(`yourstory.js:139, 169`). heartbeat 가 5분보다 낡으면 `service: "reserve"` 로 떨어져 **접수 시나리오 전체가 예약으로 빠집니다.** 테스트 첫 줄에서 `/ys/w/ping` 을 한 번 때려 heartbeat 를 세워야 합니다.

### 3-3. 검사 항목 하나 추가 — **`charge` 멱등**

제안하신 「`queued_image` 진입에서 차감 1회」에 더해, **응답이 유실되어 워커가 `charge` 를 다시 부르는 경우**를 넣어 주십시오.

`ys-worker.js:277-285` 가 원장을 세어 이중 차감을 막게 되어 있는데, **오늘 이 경로가 실제로 쓰이기 시작했습니다** — PC 파이프라인의 클라우드 호출에 재시도를 넣었기 때문입니다(08-12 통신 끊김으로 주문 하나가 죽어서 넣은 조치). 같은 `charge` 를 두 번 보내고 `ys_ledger` 의 `consume` 이 **1행인지** 봅니다.

### 확정 목록 (7건)

| # | 검사 | 잡는 것 |
| --- | --- | --- |
| 1 | 접수 → `queued_brain` | 상태 기계 입구 |
| 2 | G1 반려 시 티켓 무차감 | 과금 규칙 |
| 3 | `queued_image` 진입에서 차감 1회 | 차감 지점 단일성 |
| 4 | **`charge` 재호출 시 `consume` 1행 유지** | **멱등 (신규)** |
| 5 | `ys_ledger` consume/refund 쌍 | 실패 시 잔액 복구 |
| 6 | `ys_order_source` 암·복호 왕복 | **공용 `crypto.js` 회귀** |
| 7 | 삭제 시 원문만 파기 | 오늘 데이터로 확인된 동작의 회귀 방지 |

6번은 §2 의 키 분리를 하면 **그 작업의 안전망**이 되므로, 순서상 테스트를 먼저 두는 편이 낫습니다.

## 4. 우선순위 — **조건부 동의**

### 동의하는 부분

> *"트래픽 0 은 장애의 영향을 줄이는 것이지 분리의 비용을 늘리지 않습니다. 오히려 지금이 가장 쌉니다."*

**맞습니다. 제 1-3 의 논리가 부정확했습니다.** 「트래픽이 없어 이득이 적다」와 「지금이 가장 싸다」는 양립하고, 후자가 결정에 더 무겁습니다. D1 분리가 Q5·Q4 를 함께 개선한다는 지적도 맞습니다.

### 조건 하나 — **파일럿이 연속 성공을 낸 뒤에 착수합니다**

조사 세션이 볼 수 없었던 사실입니다. **오늘 10회 중 9회가 실패했고, 성공은 마지막 1회뿐입니다.** 그 1회도 오늘 하루 종일 고친 것들이 전부 들어간 뒤에야 나왔습니다.

지금 D1 을 가르면 **다음 실패가 파이프라인 탓인지 분리 탓인지 가를 수 없습니다.** 오늘 하루가 통째로 「원인을 어떻게 가르는가」의 싸움이었고, 아홉 번 중 여섯 번을 엉뚱한 곳(예산)을 고치며 보냈습니다. 이제 막 하나 성공한 시스템에 새 변수를 넣는 것은 그 비용을 다시 치르는 일입니다.

**착수 조건: 연속 2회 성공.** 이 조건은 며칠이 아니라 몇 시간 문제일 수 있습니다.

### 제안하는 순서

| 순위 | 항목 | 앞선 안과의 차이 |
| --- | --- | --- |
| 1 | **Q6 — 스테이징 적용 + 선적용 규칙** | 동일 |
| 2 | **§2 키 분리 (`YS_ENC_SECRET`)** | **신규 · 백업의 선행 조건** |
| 3 | **Q4-2 ys 테스트 7건** | 조사안 4위 → 3위. §2·D1 분리의 안전망이라 **앞에 와야** 합니다 |
| 4 | **Q5 백업 — 결정 + Worker cron 구현** | §2 가 끝나야 성립 |
| 5 | **Q2 D1 분리** | 조사안 3위 → 5위. **다만 순서가 아니라 조건 때문**입니다(연속 2회 성공) |
| 6 | Q1 Worker 분리 | 동일 |
| 7 | Q3 cron·폴링 | 동일 |

**이견의 실체는 순위가 아니라 조건입니다.** 조사 세션이 D1 분리를 앞세운 근거(지금이 가장 싸다)에 동의하므로, **연속 2회 성공이 확인되면 3위로 올려도 좋습니다.**

`touchUser()` 결정을 D1 분리와 함께 정해야 한다는 지적도 동의합니다.

**결론: 튜닝 문제가 아니었습니다.** 저는 여섯 번을 「예산 부족」으로 읽고 상한을 두 번 올렸는데, 그중 예산이 실제 원인이었던 것은 **1건**뿐입니다. 나머지는 위 구조 문제 셋이었고, 셋 다 오늘 고쳤습니다(앵커 G4 게이트 신설 · 3표 다수결 · 재생성 우선순위 3단계).

**주의 — 성공 1건으로 해결됐다고 보지 않습니다.** 초벌 글자 위반율이 회차마다 12.5 ~ 62.5% 로 편차가 큽니다. 연속 성공을 봐야 판단할 수 있고, **§4 의 착수 조건이 이 때문입니다.**

**돈은 전 구간에서 어긋나지 않았습니다.** 실패 9건 중 과금까지 간 6건이 전부 `consume` → `refund` 쌍으로 남았고, 성공 1건만 `refund` 없이 798원이 기록됐습니다. 조사 세션이 §1 에서 독립 확인한 그 원장입니다.

## 6. 개발 세션이 하지 않은 것 (명시)

* D1 은 **읽기 전용 SELECT** 만 했습니다. 스키마·데이터 변경 없음.
* **`git` 을 실행하지 않았습니다.** 이 문서를 포함해 `docs/handoff/` 커밋은 **Master 승인 후**입니다 — README §「이 폴더에 커밋하면 배포가 돕니다」 대로 문서 커밋을 모아서 하는 편을 권합니다.
* **위 권고 중 아무것도 실행하지 않았습니다.** §2 키 분리도 제안일 뿐 코드를 만지지 않았습니다.
* **계정 플랜은 여전히 미확인**입니다. 조사 세션의 인용(무료 플랜 기준 백분율)이 정확합니다.
* **법률·심사 판단은 하지 않았습니다.** §2 의 「키를 교체할 수 없는 시스템은 지적 항목」은 개발 관점의 사실 진술이며, 심사 통과 여부의 판단이 아닙니다.
