# 광고 리워드형 아케이드 미니게임 10종 — 기획서

기존 4종(스탑워치 · 숫자야구 · 타이핑 · 숫자기억력)에 이어 추가하는 미니게임 10종의 기획서입니다.
기존 게임이 "기록 경신형 콘텐츠"였다면, 이번 10종은 **앱에 탑재되는 광고 리워드용 미니게임**입니다.
따라서 설계 기준이 다릅니다.

---

## 1. 설계 목표

| 기준 | 값 | 이유 |
|---|---|---|
| 1판 길이 | **10~60초** | 광고(5초) 대비 플레이가 너무 길면 광고 시청 의사가 떨어지고, 너무 짧으면 광고가 콘텐츠보다 길어져 이탈합니다 |
| 규칙 설명 | **한 문장** | 튜토리얼을 읽어야 하는 게임은 리워드 매체로 부적합합니다 |
| 조작 | **탭 1종류** | 드래그·멀티터치 없음. WebView 어디서든 동일하게 동작해야 합니다 |
| 실패 시점 | **명확한 한 순간** | "아, 방금 그것만 아니었으면"이 성립해야 광고 재도전으로 이어집니다 |
| 결과 화면 | **점수 + 전체 대비 위치** | 비교 대상이 있어야 재도전 동기가 생깁니다 |

### 재도전을 만드는 세 가지 장치

1. **아깝게 끝나는 실패** — 목숨 1개, 한 번의 오답으로 종료. 종료 화면에 직전 라운드를 그대로 보여줍니다.
2. **런(run) 중 광고 보상** — 게임을 처음부터 다시 하는 게 아니라 **끊긴 지점에서 잇습니다.** 리워드 광고 시청률을 가장 크게 올리는 장치입니다.
3. **최고 기록 갱신 압박** — 결과 화면에 항상 "내 최고 기록 −N" 을 표시합니다.

## 2. 게임 10종 요약

| # | 게임 | 코드 | 조작 | 1판 | 순위 지표 | 진행 방식 |
|---|---|---|---|---|---|---|
| ⑤ | 반응속도 테스트 | `REACTION` | 초록으로 바뀌면 탭 | ~20초 | 평균 반응속도(ms) ↓ | 5시행 |
| ⑥ | 색 다른 타일 찾기 | `ODDCOLOR` | 다른 색 타일 탭 | 끝날 때까지 | 도달 라운드 ↑ | 무한 |
| ⑦ | 순서 기억 | `SEQUENCE` | 반짝인 순서대로 탭 | 끝날 때까지 | 도달 라운드 ↑ | 무한 |
| ⑧ | 숫자 순서 터치 | `NUMTAP` | 1→25 순서대로 탭 | ~35초 | 완주 시간 ↓ | 1회 완주 |
| ⑨ | 60초 암산 | `MATHRUSH` | 답 숫자 입력 | 60초 | 정답 수 ↑ | 시간제 |
| ⑩ | 색깔 말하기(스트룹) | `STROOP` | 글자의 *색* 선택 | 최대 30초 | 연속 정답 ↑ | 시간제+즉사 |
| ⑪ | 링 스톱 | `RINGSTOP` | 타겟 구간에서 탭 | 끝날 때까지 | 연속 성공 ↑ | 무한 |
| ⑫ | 순간 개수 세기 | `COUNTDOT` | 본 점 개수 입력 | 끝날 때까지 | 도달 라운드 ↑ | 무한 |
| ⑬ | 카드 짝 맞추기 | `CARDPAIR` | 카드 2장 뒤집기 | ~50초 | 뒤집기 횟수 ↓ | 1회 완주 |
| ⑭ | 이겨라 / 져라 | `RPSFLASH` | 지시대로 손 선택 | 끝날 때까지 | 연속 정답 ↑ | 무한+즉사 |

기술적으로는 두 가지 진행 방식만 있습니다.

- **ENDLESS** — 라운드마다 서버에 왕복합니다. 서버가 다음 라운드를 만들고 정답을 판정합니다.
  (`ODDCOLOR` `SEQUENCE` `RINGSTOP` `COUNTDOT` `CARDPAIR`)
- **BATCH** — 시작할 때 서버가 문제 묶음을 발급하고, 클라이언트가 로컬에서 빠르게 진행한 뒤
  전체 답안과 문항별 응답 시간을 한 번에 제출합니다. 서버가 전부 다시 채점합니다.
  (`REACTION` `NUMTAP` `MATHRUSH` `STROOP` `RPSFLASH`)

BATCH를 쓰는 이유는 **반응속도가 지표인 게임에서 네트워크 왕복이 기록에 섞이면 안 되기 때문**입니다.
1초짜리 라운드에 150ms 왕복을 넣으면 회선 품질을 재는 게임이 됩니다.
(기존 스탑워치에서 내린 것과 같은 판단입니다 — README「기획서와 다르게 구현한 부분」 참조)

## 3. 광고 설계

### 3.1 트리거 3종 (모든 아케이드 게임 공통)

| 트리거 | 유형 | 시점 | 보상 | 한도 |
|---|---|---|---|---|
| `{GAME}_ATTEMPT` | Rewarded | 오늘 도전 기회 소진 | 기회 +1 | **하루 5회** |
| `{GAME}_BOOST` | Rewarded | **런 진행 중** | 게임별로 다름(3.2) | **1런당 2회** |
| `{GAME}_STATS` | Interstitial | 전체 통계·랭킹 열람 | 30분 열람 해제 | 없음 |

기본 도전 기회는 게임당 **하루 5회**, 광고로 최대 **+5회** → 하루 최대 10판입니다.
동일 IP 하루 광고 20회 제한(기존 `COMMON.IP_AD_VIEWS_PER_DAY`)은 그대로 적용됩니다.

### 3.2 `_BOOST` — 게임별 보상 (핵심 장치)

"처음부터 다시"가 아니라 **끊긴 지점에서 잇는** 보상만 넣습니다.

| 게임 | 광고 1회 보상 | 사용자가 느끼는 것 |
|---|---|---|
| `REACTION` | 시행 +1회 (7시행 중 **좋은 5개**만 채택) | 방금 망친 한 판을 버릴 수 있다 |
| `ODDCOLOR` | 목숨 +1 (같은 라운드 재도전) | 라운드 14에서 안 끝난다 |
| `SEQUENCE` | 목숨 +1 (같은 라운드 새 문제) | 기억한 게 아깝지 않다 |
| `MATHRUSH` | 제한 시간 **+15초** | 지금 흐름이 좋은데 더 풀 수 있다 |
| `STROOP` | 오답 1회 면제 | 연속이 안 끊긴다 |
| `RINGSTOP` | 목숨 +1 | 연속 기록이 살아난다 |
| `COUNTDOT` | 목숨 +1 | 3목숨이 5목숨이 된다 |
| `CARDPAIR` | **아직 못 맞춘 한 쌍의 위치 공개** | 막힌 판이 풀린다 |
| `RPSFLASH` | 오답 1회 면제 | 연속이 안 끊긴다 |
| `NUMTAP` | (없음 — 기록 게임) | |

### 3.3 랭킹 공정성 — `+` 버킷

광고 보상을 쓴 런은 안 쓴 런보다 유리합니다. 같은 순위표에 넣으면 순위표가 광고 소비량 순위가 됩니다.
그래서 **보상을 한 번이라도 쓴 런은 bucket 뒤에 `+` 가 붙어 별도 리그로 집계**합니다.

```
ODDCOLOR : "all"  (무보상)  /  "all+"  (보상 사용)
MATHRUSH : "60s"            /  "75s" · "90s"   ← 시간 연장은 연장된 시간이 곧 리그
CARDPAIR : "clean"          /  "clean+"
```

사용자에게는 결과 화면에 "광고 보상 리그" 라고만 표시합니다.
이 규칙은 공통 엔진(`src/lib/arcade.js`)이 자동 적용하므로 게임별 구현이 필요 없습니다.

### 3.4 광고를 붙이지 않은 곳

- **게임 시작 전 강제 전면광고 없음.** 첫 판까지의 마찰이 이탈률에 가장 크게 작용합니다.
- **결과 화면 자동 재생 광고 없음.** 재도전 버튼을 누르는 흐름을 끊습니다.
- 광고는 전부 **사용자가 버튼을 눌러 시작**합니다. 보상 카드(`renderRewardCard`)는 기존 규칙대로
  주 버튼보다 시각적으로 약한 점선 카드로 둡니다.

## 4. 게임별 상세

수치는 전부 `src/lib/config.js` 의 `ARCADE` 에 모아 두었습니다. 밸런싱은 그 파일만 고치면 됩니다.

### ⑤ 반응속도 테스트 `REACTION` — BATCH

> 화면이 초록으로 바뀌는 순간 탭하세요. 5번의 평균이 기록입니다.

- 시행 5회. 각 시행 대기 시간은 서버가 **1.2~4.5초 사이 난수**로 미리 발급합니다.
- 초록 전에 탭하면 **부정출발(false start)** — 그 시행은 무효 처리되고 기록에 넣지 않습니다.
- 유효 시행이 하나도 없으면 실패로 종료합니다.
- 순위 지표: 채택된 시행의 **평균 ms (작을수록 상위)**.
- `_BOOST`: 시행 +1. 총 7시행까지 늘어나며 **좋은 5개만 채택**합니다.
- 검증: 100ms 미만 반응은 사람이 낼 수 없으므로 이상치(`suspect`)로 표시해 통계에서 제외합니다.

### ⑥ 색 다른 타일 찾기 `ODDCOLOR` — ENDLESS

> 하나만 색이 다릅니다. 찾아서 탭하세요.

- 라운드 r 의 격자: 3라운드마다 한 단계씩 커집니다. 2×2 → 6×6.
- 색 차이: 라운드마다 좁아집니다 (HSL 명도차 26% → 최소 2.5%).
- 라운드 제한 시간: 6.0초 → 최소 2.5초.
- 목숨 1. 오답 또는 시간 초과 시 종료.
- 순위 지표: **클리어한 라운드 수 (많을수록 상위)**.

### ⑦ 순서 기억 `SEQUENCE` — ENDLESS

> 반짝인 순서를 그대로 따라 누르세요.

- 3×3 = 9칸 패드. 라운드 r 의 시퀀스 길이 = r + 2 (3부터 시작).
- 점멸 간격: 620ms → 최소 280ms.
- 입력 제한 시간: 시퀀스 길이 × 2.5초.
- 한 칸이라도 틀리면 종료. 목숨 1.
- 순위 지표: **클리어한 라운드 수**.

### ⑧ 숫자 순서 터치 `NUMTAP` — BATCH

> 1부터 25까지 순서대로. 빠를수록 좋습니다. (슐테 테이블)

- 5×5 격자에 1~25를 서버가 셔플해서 배치합니다. 배치는 화면에 그대로 보이는 정보라 숨기지 않습니다.
- 잘못 누른 탭은 무시하되 **오탭 1회당 +0.5초** 페널티를 최종 기록에 더합니다.
- 순위 지표: **최종 기록 ms (작을수록 상위)**.
- 검증: 탭 간격 90ms 미만이 **네 번을 넘고 전체의 20% 이상**일 때 자동 입력으로 보고 이상치 처리합니다.
  (한두 번 유난히 빨랐던 것 — 인접한 칸을 연달아 누른 경우 — 까지 잡으면 정상 사용자를 오탐합니다)
- `_BOOST` 없음. 순수 기록 경신 게임이라 도전 기회 충전만으로 재도전이 일어납니다.

### ⑨ 60초 암산 `MATHRUSH` — BATCH

> 60초 동안 몇 문제나 풀 수 있나요?

- 난이도가 문항 순서에 따라 올라갑니다.
  1~10번 두 자리 덧뺄셈 → 11~25번 한 자리 곱셈 → 26번부터 세 자리 혼합.
- 정답 +1점. 오답은 즉시 다음 문제로 넘어가고 **남은 시간 −3초**.
- `_BOOST`: **+15초**. 최대 90초까지. 연장한 런은 `75s` / `90s` 리그로 따로 집계합니다.
- 순위 지표: **정답 수 (많을수록 상위)**, 동점이면 평균 응답 시간이 짧은 쪽.

### ⑩ 색깔 말하기 `STROOP` — BATCH

> 글자의 **뜻**이 아니라 **색**을 고르세요. 하나라도 틀리면 끝.

- 문제: 색 이름 단어(빨강/파랑/초록/노랑/보라)를 다른 색으로 표시. 4지선다.
- 문항 제한 시간 2.5초 → 최소 1.2초. 전체 제한 30초.
- 오답 또는 시간 초과 시 즉시 종료.
- `_BOOST`: 오답 1회 면제 (연속 유지).
- 순위 지표: **연속 정답 수**, 동점이면 평균 응답 시간.

### ⑪ 링 스톱 `RINGSTOP` — ENDLESS

> 원을 도는 점이 밝은 구간에 들어왔을 때 탭하세요.

- 각속도: 120°/s → 최대 420°/s. 타겟 구간: 46° → 최소 14°.
- 클라이언트는 탭한 순간의 **각도와 경과 시간**을 함께 보냅니다.
- 목숨 1. 실패 시 종료.
- 순위 지표: **연속 성공 횟수**.
- 검증: 판정에 클라이언트가 보낸 각도를 쓰지 않습니다. 서버가 `시작각 + 각속도 × 경과시간` 으로
  각도를 **직접 재현**해서 판정합니다. 신고 각도는 재현값과 대조하는 정합성 확인에만 쓰고,
  8° 넘게 어긋나면 이상치로 표시합니다.
  경과 시간은 서버가 라운드를 발급한 시각 기준 시간창 안이어야 하며, 네트워크 지연 수준(700ms)을
  넘게 어긋나면 서버 관측값으로 판정합니다.

### ⑫ 순간 개수 세기 `COUNTDOT` — ENDLESS

> 점이 몇 개였나요? 0.4초만 보여줍니다.

- 점 개수: 3개 ~ (4 + 라운드×2, 최대 24개).
- 노출 시간: 420ms → 최소 160ms.
- 목숨 3. 틀릴 때마다 −1.
- 숫자패드(`mountNumpad`)로 입력합니다.
- 순위 지표: **클리어한 라운드 수**.

### ⑬ 카드 짝 맞추기 `CARDPAIR` — ENDLESS

> 4×4, 8쌍. 적게 뒤집을수록 좋습니다.

- 카드 배치는 **서버 세션에만 있고 클라이언트로 내려가지 않습니다.**
  카드를 뒤집을 때마다 서버에 물어보고, 서버가 그 자리의 그림 하나만 알려 줍니다.
  → 개발자도구로 배치를 미리 볼 수 있는 경로가 없습니다. (숫자야구와 같은 구조)
- 순위 지표: **뒤집기 횟수 (적을수록 상위)**, 동점이면 소요 시간.
- `_BOOST`: 아직 못 맞춘 카드 중 **한 쌍의 위치를 공개**합니다. 1런당 2회.

### ⑭ 이겨라 / 져라 `RPSFLASH` — BATCH

> 「이겨라」면 이기는 손, 「져라」면 지는 손. 1초 안에.

- 라운드마다 상대의 손(✊✌✋)과 지시(이겨라 / 져라 / 비겨라)가 함께 제시됩니다.
- 문항 제한 시간 1.4초 → 최소 0.6초.
- 틀리거나 시간을 넘기면 즉시 종료.
- `_BOOST`: 오답 1회 면제.
- 순위 지표: **연속 정답 수**, 동점이면 평균 응답 시간.

## 5. 공통 모듈 준수 사항

새 게임은 기존 공통 모듈 규칙을 그대로 따릅니다. 새로 만든 것은 아래 두 개뿐입니다.

### 5.1 재사용하는 기존 모듈 (수정 없음)

| 모듈 | 재사용 내용 |
|---|---|
| `public/shared/base.css` | 색·라운드·여백 토큰, `.card` `.btn` `.screen` `.stats` `.chart` `.rank-row` `.reward` |

### 5.2 새로 추가하는 공통 모듈

| 파일 | 역할 |
|---|---|
| `src/lib/arcade.js` | 런 엔진. 세션 생성·라운드 판정·목숨·보상·버킷·결과 저장을 전부 담당 |
| `public/shared/run.js` | 클라이언트 런 헬퍼. API 래퍼, 광고 게이트 통계 흐름, 목숨 표시, 결과 카드, 카운트다운 |

게임별 서버 파일(`src/games/*.js`)은 **spec 객체 하나**만 내보냅니다.

```js
export const spec = {
  game: "ODDCOLOR",
  mode: "ENDLESS",
  makeRound(roundNo, meta),        // 다음 라운드 생성 → { pub, secret, limitMs }
  judgeRound({ answer, secret, ... }),  // 판정 → { correct, data }
  bucketOf(meta),                  // 리그 키 ('+' 는 엔진이 자동으로 붙임)
  rankMetricOf(meta),              // 작을수록 좋은 값으로 정규화
  applyBoost(meta),                // 광고 보상 적용
};
```

라운드 생성·판정 규칙 외의 것(기회 차감, 세션 만료, 중복 제출, 이상치 표시, 백분위 계산,
최고 기록 갱신, 광고 한도)은 엔진이 처리하므로 게임 파일에 중복 코드가 없습니다.

## 6. 어뷰징 방지 — 게임별 검증 수단

기존 4종에 적용한 원칙(정답 비노출 / 서버 재채점 / 시간창 검증 / 중복 제출 차단)을 그대로 씁니다.

| 게임 | 서버가 실제로 막을 수 있는 것 | 남는 한계 |
|---|---|---|
| `CARDPAIR` | 배치가 서버에만 있음 → **완전 차단** | 없음 |
| `RINGSTOP` | 판정 각도를 서버가 **직접 재현**. 클라이언트 각도는 판정에 쓰지 않음 | 경과 시간은 클라이언트 신고값이라, 700ms 시간창 안에서 유리한 시각을 고르는 조작은 남음 |
| `ODDCOLOR` `SEQUENCE` `COUNTDOT` | 정답 판정이 전부 서버. 결과 위조 불가 | 문제를 화면에 그려야 하므로 개발자도구로 정답을 읽는 것은 막을 수 없음 |
| `REACTION` `NUMTAP` | 시간창 검증 + 인간 하한(100ms / 탭 간격 90ms) 이상치 처리 | 사람이 낼 수 있는 범위 안에서의 미세 조작 |
| `MATHRUSH` `STROOP` `RPSFLASH` | 답안 서버 재채점 + 문항별 응답 시간 하한 검증 | 문제 자체가 자명하므로 자동화 스크립트는 항상 만점 → 이상치 처리로만 대응 |

**공통 처리**: 이상치는 거부하지 않고 `results.suspect = 1` 로 저장합니다.
사용자에게는 기록을 보여주되 전체 통계·랭킹에서만 제외합니다.
(정상 사용자를 오탐으로 차단하는 것보다 통계 오염을 막는 쪽이 안전합니다 — 기존 스탑워치와 동일한 판단)

**응답 시간 하한은 비율로 판단합니다.** 한 문항만 하한 미만이어도 이상치로 처리하면
손가락이 미끄러져 두 번 눌린 것만으로 판 전체가 순위에서 빠집니다. 자동화는 거의 모든 문항이
빠르므로, "하한 미만이 네 개를 넘고 동시에 전체의 20% 이상" 일 때만 이상치로 봅니다.
예외는 반응속도 게임입니다 — 100ms 미만 반응은 생리적으로 불가능하고 그 값이 채택되면
평균을 그대로 망가뜨리므로, 한 번이라도 나오면 이상치로 처리합니다.

**시간 제한은 클라이언트도 지켜야 합니다.** 제한 시간 종료를 `requestAnimationFrame` 에만
맡기면 앱을 잠깐 벗어난 사이 rAF 가 멈춰 게임이 계속 진행되고, 결과적으로 실제 플레이 시간이
제한 시간을 넘겨 서버 검증에서 이상치로 걸립니다. 사용자는 잠시 앱을 벗어났을 뿐인데 기록이
순위에 오르지 않는 셈입니다. 그래서 `public/shared/run.js` 의 `countdown` 은 화면 갱신만
rAF 로 하고 **종료 시각은 `setTimeout` 으로 따로 걸어 두고, 복귀 시점에 한 번 더 확인**합니다.

자동화 스크립트를 원리적으로 막으려면 문제를 서버에서 이미지로 렌더링해야 하는데,
리워드 광고용 미니게임에서 그 비용을 치를 이유가 없습니다.
**광고 보상은 판정 결과가 아니라 광고 시청 여부에 걸려 있고, 광고 한도는 서버가 별도로 강제**하므로
랭킹 조작의 실익이 광고 수익에 영향을 주지 않습니다.

## 10. 규모 (10만 DAU 기준 측정)

로컬 D1 에 실제로 행을 넣고 잰 값입니다. 추정이 아니라 실측입니다.

### 10.1 고친 것

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| 백분위 계산 (매 판) | 100만 행 75ms · 300만 행 계속 증가 | **14~16ms 고정** |
| 분포 히스토그램 | 100만 행 605ms + **100만 개 배열이 Worker 메모리로** | **37ms, 8행만 반환** |
| 리그별 집계 | 100만 행 1,886ms | **22~25ms 고정** |
| 순위표 TOP 20 | 300만 행 161ms (동점자 정렬) | **0ms** |
| 내 순위 | 300만 행 85ms | **15ms** |
| 세션 1건 크기 (닫힌 뒤) | 2,032 bytes | **2 bytes** |

핵심은 두 가지입니다.

**집계 대상을 최근 `COMMON.STATS_WINDOW`(5만) 건으로 고정.** 백분위와 분포는 "지금 사람들과
비교해 내가 어디쯤인가" 를 보여 주는 값이라 전체 역사가 필요하지 않습니다. 창을 고정하니
기록이 100만이든 300만이든 비용이 같습니다. 순위표(TOP 20)와 개인 최고 기록은 창과 무관하게
전체 기준입니다 — 그쪽은 인덱스로 앞 20건만 읽으면 되므로 창이 필요 없습니다.

**히스토그램 계산을 SQL 로 이동.** 예전에는 리그의 모든 `rank_metric` 을 Worker 로 가져와
세었습니다. 100만 건이면 100만 개짜리 배열이 Worker 메모리(128MB)로 들어옵니다 — 언젠가
반드시 터지는 구조였습니다. 지금은 응답이 항상 구간 8행입니다.

### 10.2 용량 — 가장 위험했던 지점

10만 DAU × 14게임 × 하루 3판 = **하루 420만 세션**. 세션 1건이 평균 2KB 였습니다
(스트룹·이겨라/져라는 문항 120개의 정답과 제한 시간, 60초 암산은 정답 80개를 담습니다).

```
하루 증가    8.19 GB
7일 누적    57.3 GB
30일 누적  245.7 GB      ← D1 데이터베이스 상한 10GB
```

**이틀도 못 버팁니다.** 두 가지로 해결했습니다.

1. **닫히는 즉시 정답을 비웁니다.** 닫힌 세션의 정답은 다시 쓰이지 않습니다 — 결과는 이미
   `results` 에 들어갔고 `getOpenSession` 은 OPEN 만 봅니다. 2,032 → 2 bytes.
   이제 큰 값을 가진 세션은 "지금 플레이 중인 사람" 수에만 비례하며, 누적 사용자와 무관합니다.
2. **Cron 이 오래된 세션 행을 지웁니다.** 10분마다, 6시간 지난 것부터 회당 최대 5,000건.
   게임 기록은 `results` 에 남으므로 통계·순위에 영향이 없습니다.

`results` 는 계속 쌓이지만 1건이 약 600 bytes 라 하루 2.5GB 입니다. 이것도 언젠가는
상한에 닿으므로, 실사용 데이터가 쌓이면 **오래된 결과의 `detail_json` 을 비우는 정리**를
추가하는 것이 다음 단계입니다 (순위·통계는 `rank_metric` 과 `score` 만 쓰므로 영향 없음).

### 10.3 남은 한계

- **D1 쓰기 처리량.** 하루 420만 세션 = 초당 약 49건, 라운드 갱신까지 더하면 그 몇 배입니다.
  D1 단일 데이터베이스로 이 쓰기를 감당할 수 있는지는 실서비스 트래픽으로 확인해야 합니다.
  넘으면 세션 상태를 Durable Object 로 옮기는 것이 정석입니다 (라운드 왕복도 함께 빨라집니다).
- **라운드 왕복 ~470ms.** D1 쿼리 1회가 약 150ms 이고 라운드는 읽기+쓰기 2회입니다.
  카드 짝 맞추기는 클라이언트에서 지연을 흡수했고, 나머지 게임은 라운드 간격이 2~6초라
  문제가 되지 않습니다.

## 11. 이번 작업에 포함하지 않은 것

- **실제 광고 SDK 연동** — 기존과 동일하게 목업입니다. 채울 파일도 그대로 두 개
  (`public/shared/ad.js`, `src/lib/adverify.js`)이며, 게임이 10개 늘어도 연동 작업량은 늘지 않습니다.
- **일일 미션 / 연속 출석 / 재화** — 리텐션 장치는 게임 단위가 아니라 앱 단위 설계가 필요합니다.
- **사운드 / 햅틱** — WebView 브리지 스펙을 받은 뒤 공통 모듈로 한 번에 넣는 편이 낫습니다.
- **밸런싱 검증** — 난이도 곡선 수치는 초안입니다. 실사용 데이터(`results`)가 쌓이면
  `config.js` 의 `ARCADE` 값만 조정하면 됩니다.
