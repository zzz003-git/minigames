# ㉕ 오늘의 한 잔 — 구현 명세

기획서 `../reward-minigame-research/plans/2026-07-30/PLAN-15_오늘의한잔.md`
(`IDEA-2026-0015`, 안정형 / 엔진 D 드래그·분류 — 붓기 변형)를 구현한 문서입니다.

원안(IDEA-0003)은 **재미가 7일 뒤에 있어** 첫 10초 게이트에서 탈락했습니다. 이 개정은
그것을 첫 터치로 끌어온 것이고, 구현도 그 전제를 따릅니다 — 하루 1잔 완결입니다.

---

## 1. 규격에서 벗어난 항목

| 항목 | 규격 | 이 게임 | 이유 |
|---|---|---|---|
| 조작 | 탭 1종류 | **누름 지속(홀드)** | 손맛이 이 기획의 존재 이유입니다(기획서 5장). 탭으로 바꾸면 「양을 조절한다」가 사라져 게임이 남지 않습니다 |
| 도전 기회 | 하루 5회 | 하루 **1잔** | 하루의 끝에 놓는 리추얼 포지셔닝(기획서 3장). ⑲⑳ 과 같은 값입니다 |
| `_ATTEMPT` 광고 | 하루 5회 | **0회** | 잔을 더 주지 않습니다. 광고는 「그 층만 다시 붓기」 하나뿐입니다(기획서 8장) |
| 영속 상태 | 없음 | **앨범**(`pour_album`) | 만든 잔이 쌓이는 것이 재방문 장치입니다(기획서 9장) |

**대체 경로**: 키보드·보조기기는 **Enter/Space 를 누르고 있는 동안** 같은 값이 오릅니다
(`keydown` → 시작, `keyup` → 확정). 자동 반복(`e.repeat`)은 무시하므로 누르고 있는
시간이 그대로 양이 됩니다.

---

## 2. 게임 규칙 (구현값)

| 항목 | 값 | 근거 |
|---|---|---|
| 층 | **3층** (병 3개) | 기획서 4장 |
| 목표선 | 잔의 55~92% 무작위 · 첫 주는 78% 이상 | 기획서 6장 초보자 |
| 붓는 속도 | 1초에 잔의 **45%** | 한 층을 1~2초에 부을 수 있는 속도 |
| 홀드 상한 | 4초 | 이 이상은 잔을 넘깁니다 |
| 등급 | 딱 맞음 ≤3% · 근접 ≤8% · 여유 · 넘침 | 기획서 4장 4번 |
| 실패 | **없음** | 넘침은 미달성이지 손실이 아닙니다(기획서 4장 5번) |

수치는 전부 `src/lib/config.js` 의 `ARCADE.POUR` 에 있습니다.

**등급을 숫자로 표시하지 않습니다.** 「87점」처럼 쓰면 원안의 채점표 문제가 되살아납니다
(기획서 16장 4번). 화면에는 말(딱 맞음/근접)과 잔의 그림만 씁니다.

## 3. 영속 상태 — 앨범

`migrations/0012_pour_album.sql`. 색 조합 문자열만 남깁니다(`"pink-yellow-cream"`).
잔 그림을 저장하지 않는 이유는 화면에 필요한 것이 「이 조합을 만들어 봤는가」뿐이고,
그림은 조합에서 다시 그릴 수 있기 때문입니다. 최근 60개만 보관합니다.

`initSecret` 에서 한 번 읽고 `onRunEnd` 에서 한 번 씁니다 — ⑲⑳ 과 같은 훅 사용입니다.

---

## 4. 부은 양을 어떻게 믿는가

부은 양은 클라이언트가 계산해 보냅니다(누른 시간 × 속도). 그래서 서버는 **양과 누른
시간이 비례하는지** 검사합니다.

```
기대 양 = (누른 시간 / 1000) × POUR_RATE
|기대 양 − 신고 양| > 0.12  →  거친 신고로 셈
거친 신고가 2회 이상  →  이상치(suspect)
```

판정 자체는 신고 값으로 합니다(막으면 정상 플레이가 손해를 봅니다). 이상치로 표시된
판은 순위·개인 최고 기록에 남지 않습니다. 스탑워치·링 스톱과 같은 성질의 한계이고
같은 결론입니다(README 「남아 있는 한계」).

## 5. 구원 광고

넘친 판에서만 「그 층만 다시 붓기」를 제안합니다(기획서 8장). `applyBoost` 는
**마지막 층만 걷어내고** 커서를 하나 되돌립니다 — 앞 층은 그대로 남습니다.
버튼 문구에 **「다시 부어도 지금 층은 그대로예요」**를 넣는 것이 필수입니다
(재검증 교훈 1 — 손해 없음을 문자로 쓴다).

이 규칙은 서버 왕복으로 재현하기 어렵습니다(하루 1잔이라 광고 자리를 만들려면 판을 또
열어야 합니다). 그래서 `npm run test:api` 가 spec 을 직접 불러 결정적으로 검사합니다
(`pourRedoRule`) — ⑲ 의 `storeShelfRules` 와 같은 이유입니다.

---

## 6. 순위 지표

**목표선과의 차이**입니다(작을수록 상위). 넘친 판은 `1 + 차이` 로 보내 최하위 쪽에
둡니다 — 잃는 것은 없지만 순위는 아닙니다. 획득 포인트로 순위를 세우면 새 조합 발견
보너스가 섞여 「정확히 부은 사람」이 아니라 「처음 만든 사람」이 상위가 됩니다.
