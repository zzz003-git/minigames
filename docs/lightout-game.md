# ㉙ 소등 — 구현 명세

기획서 `../reward-minigame-research/plans/2026-08-03/PLAN-24_소등.md`
(`IDEA-2026-0024`, 안정형 / 엔진 A 타이밍 — 누름 지속) 를 구현한 문서입니다.

자사 기획 24건이 전부 **밝은 곳·서 있음·급함** 맥락이었습니다. 이것이 **취침 맥락을
조건으로 잡은 첫 기획**이고, 구현도 그 전제를 따릅니다 — 화면이 어디서도 밝아지지 않습니다.

---

## 1. 규격에서 벗어난 항목

| 항목 | 규격 | 이 게임 | 이유 |
|---|---|---|---|
| 조작 | 탭 1종류 | **누름 지속(홀드)** | 손맛(진동이 잦아들다 툭 멎는 감각)이 기획의 존재 이유입니다(기획서 5장). 탭으로 바꾸면 「끝까지 누른다」가 사라져 게임이 남지 않습니다 |
| 1판 길이 | 10~60초 | 30~50초 | 규격 안입니다. 다만 하루 3방을 합치면 약 2분입니다 |
| 도전 기회 | 하루 5회 | 하루 **3방** | 기획서 4장 7번 |
| `_ATTEMPT` 광고 | 하루 5회 | **0회** | 방을 더 주지 않습니다. 광고는 「이 방, 한 번 더」 하나뿐입니다(기획서 8장) |
| 영속 상태 | 없음 | **어제의 나**(`lightout_daily`) | 재방문 장치가 어제 기록입니다(§3) |

**대체 경로**: 키보드·보조기기는 Tab 으로 불빛을 옮기고 **Enter/Space 를 누르고 있는
동안** 같은 값이 흐릅니다(`keydown` → 시작, `keyup` → 확정). 자동 반복(`e.repeat`)은
무시하므로 누르고 있는 시간이 그대로 값이 됩니다 — ㉕ 오늘의 한 잔과 같은 방식입니다.

---

## 2. 게임 규칙 (구현값)

| 항목 | 값 | 근거 |
|---|---|---|
| 불빛 수 | 첫 방 **16개** · 이후 **24개** | 기획서 10장 (첫 방은 감을 잡게) |
| 꺼지는 데 걸리는 시간 | **400~800ms** (불빛마다 다름) | 기획서 4장 2번 |
| 불빛 사이 최소 간격 | 무대 짧은 변의 **0.15** | 겹치면 엄지 하나가 두 개를 건드립니다(기획서 10장) |
| 제한 시간 | **없음** | 기획서 4장 8번. 화면에 카운트다운이 없습니다 |
| 실패 | **없음** | 방을 다 끄는 것이 유일한 종료입니다 |
| 마지막 뒤 정적 | **600ms** 완전한 검정 | 기획서 4장 6번 |
| 입력 잠금 | 화면 전환 뒤 **400ms** | 기획서 8장 0-H |

수치는 전부 `src/lib/config.js` 의 `ARCADE.LIGHTOUT` 에 있습니다.

**불빛 크기가 곧 필요 시간입니다.** 오래 눌러야 하는 불빛일수록 큽니다 — 글로 설명하지
않아도 손이 먼저 압니다. 그래서 필요 시간을 화면에 내려보냅니다(숨겨 봐야 지킬 것이
없고, 숨기면 화면이 크기를 그릴 수 없습니다).

**불빛끼리 상호작용시키지 않습니다.** 하나를 끄면 옆이 밝아지는 규칙을 넣는 순간
「순서 최적화」가 핵심이 되고, 그건 몸의 동사가 아니라 판단입니다(기획서 5장).

## 3. 영속 상태 — 어제의 나

`migrations/0014_lightout_daily.sql`. 하루 한 행이고 두 가지를 씁니다.

```
rooms    오늘 완주한 방 수 → 다음 방의 불빛 개수(첫 방 16 · 이후 24)
best_ms  오늘의 최고 기록  → 내일의 「어제 기록」
```

**개인 최고 기록으로 대신할 수 없습니다.** 개인 최고는 한 번 잘 나오면 몇 달을 못 넘고,
그러면 8장의 광고 조건(「어제보다 느렸을 때만 제안한다」)이 거의 항상 참이 되어
구원이 아니라 관문이 됩니다.

`best_ms` 는 **더 빠를 때만** 바뀝니다(SQL 의 `CASE` 한 줄). 기획서 8장 ⓐ 문구
「다시 해도 지금 기록 38초는 그대로예요. 더 빠를 때만 바뀌어요」가 서버 로직으로
보장돼야 쓸 수 있는 문구이기 때문입니다.

`initSecret` 에서 한 번 읽고 `onRunEnd` 에서 한 번 씁니다 — ⑲⑳㉕ 와 같은 훅 사용입니다.
이어하기로 여러 번 돈 판도 **한 번만** 셉니다(방 하나가 도전 기회 하나입니다).

## 4. 방 하나가 라운드 하나인 이유

불빛마다 서버에 물으면 24 × 470ms 가 왕복에 들어가 30~50초짜리 판이 성립하지 않습니다.
그래서 화면은 불빛별 유지 시간을 모으기만 하고 **방을 다 끄면 한 번에** 보냅니다.

㉘ 톡톡처럼 조각으로 나누지 않은 이유는 두 가지입니다 — 방이 30~50초라 나눌 이유가
없고, 나누면 「완전한 어둠」이라는 종료 순간이 서버에 여러 번 도착합니다.

**끄는 중인 방이 있으면 `makeRound` 가 `null` 을 돌려줍니다.** 엔진은 판이 끝나지 않은
모든 판정 뒤에 다음 라운드를 만드는데, 이 게임은 불빛이 남은 신고를 반려하고 방을
살려 두기 때문입니다. 여기서 새 방을 뽑으면 **화면은 옛 방을 보여 주는데 서버는 새 방을
채점**하게 되고, 필요 시간이 어긋나 정상 플레이가 이상치로 찍힙니다(실제로 걸렸습니다).

---

## 5. 기록을 어떻게 믿는가

화면이 보내는 것은 「몇 번 불빛을 몇 ms 눌렀는가」와 방 전체 시간입니다.
서버가 보는 것은 셋입니다(`gradeRoom`).

```
① 다 껐는가         불빛 번호가 빠짐없이 한 번씩 와야 합니다
② 시간이 성립하는가  누른 시간의 합 ≤ 방이 열린 뒤 흐른 시간   ← 유일한 물리적 상한
                    기록 = clamp(신고값, 누른 시간의 합, 방이 열린 시간)
③ 사람인가          필요 시간 대비 **초과분**의 표준편차 < 12ms 면 매크로
```

**신고한 총 시간에 상한을 따로 걸지 않습니다.** 이 게임은 작을수록 상위라 부풀린 신고는
자해입니다. 막아야 하는 것은 줄여 신고하는 쪽이고 그건 하한이 잡습니다. 상한을 신고값에
걸었더니 정직하게 10초를 적은 사람은 거부되고 1초라고 적은 사람은 통과하는 뒤집힌
규칙이 됐습니다.

**유지 시간 자체의 균일함은 신호가 아닙니다.** 불빛마다 필요 시간이 400~800ms 로 다르니
필요 시간에 딱 맞춰 누르는 매크로도 유지 시간의 분산은 크게 나옵니다. 사람은 꺼진 것을
보고 떼므로 **초과분**이 수십 ms 씩 흔들리고, 매크로는 그 값이 늘 같습니다.

이상치는 거부하지 않고 `suspect` 로 표시합니다 — 기존 전 게임과 같은 결론입니다.

## 6. 이긴 사람에게는 광고를 팔지 않는다

기획서 8장은 「어제보다 빨랐다 → 광고 버튼을 띄우지 않는다」입니다. 화면 조건문으로 두면
화면을 고쳐 되살릴 수 있으므로 **서버가 판의 끝맺음으로** 가릅니다.

```
어제보다 빨랐다 → done: true    완주로 확정. 이어하기 화면이 오지 않습니다
어제보다 느렸다 → fatal: true   소진 → 「이어하기 아니면 종료」
```

처음에는 `meta.boosts` 를 상한까지 채워 막았는데, 그러면 **광고를 보지도 않은 판이
'+' 리그로 갑니다**(브라우저 확인에서 결과 화면에 「광고 보상 리그」가 찍혔습니다).
순위표가 광고 소비량 순위가 되는 것을 막으려고 만든 리그인데 그 반대로 오염되는
셈이라, 보상 사용량이 아니라 판의 끝맺음으로 가르는 지금 방식으로 바꿨습니다.

「이 방, 한 번 더」는 **배치를 새로 뽑습니다.** 같은 배치면 외운 동선으로 기록이 나와
「더 빠를 때만 갱신」이 실력이 아니라 암기가 됩니다.

---

## 7. 화면이 밝아지지 않는다

취침 맥락이 전제입니다(기획서 3장 · 화면 밝기 최저 · 누운 채 · 소리 끔).

- `body` 에 `game--nightmode` 를 붙여 **결과 화면의 색종이(`.confetti`)를 끕니다.**
  밝기로 축하하지 않고 잔광으로만 합니다.
- 소리를 쓰지 않습니다. 진동은 **감쇠 패턴**(강→약→정지)이고, 진동을 끈 기기에서는
  잔광의 수축이 그 자리를 대신합니다.
- 방이 어두워질수록 남은 불빛의 **잔광이 넓어집니다**(`--dark`). 화면이 밝아지는 것이
  아니라 남은 것이 도드라지는 것입니다 — 어둠 속에서 못 찾는 일이 없게(기획서 4장 5번).

---

## 8. 순위 지표

**방을 끄는 데 걸린 시간**입니다(작을수록 상위). 방을 못 끝낸 판(중도 종료)은 기록이
없으므로 `ROOM_MAX_MS` 로 보내 최하위 쪽에 둡니다 — 잃는 것은 없지만 순위는 아닙니다
(㉕ 오늘의 한 잔과 같은 처리).
