# ⑲ 내 가게 채우기 — 구현 명세

기획서 `../reward-minigame-research/plans/2026-07-29/PLAN-13_내가게채우기.md`
(`IDEA-2026-0013`, 안정형 / 엔진 E 수집·성장)를 이 저장소로 구현한 문서입니다.

앞의 18종과 **판이 끝난 뒤에 남는 것이 있다**는 점이 다릅니다. 나머지 게임은 판이 끝나면
기록만 남고 상태는 사라지지만, 이 게임은 진열한 선반이 계정에 영구히 쌓입니다.

---

## 1. 왜 이 게임인가 (기획서 2장 요약)

기획서의 출발점은 데이터가 아니라 **원리**입니다.

- **정리욕** — 어질러진 것을 채우고 정돈하는 것 자체가 보상. 반응속도가 필요 없어
  주력층(30~65세)에 맞습니다.
- **수집·완성(도감)** — 광고주 상품이 곧 도감 아이템이 되는 구조라, 재미와 광고가
  따로 놀지 않습니다. 진열대가 곧 광고 지면입니다.

자사 배포분에 **수집·성장형이 한 종도 없었습니다.** 조사된 국내 E형은 전부 "조작이 결과를
바꾸지 않는" 자동 적립형(스탬프·채굴·나무)이고, 손으로 채우는 성장형은 시장에도 없습니다.

---

## 2. 게임 규칙 (구현값)

| 항목 | 값 | 근거 |
|---|---|---|
| 진행 방식 | `ENDLESS` | 상품 하나를 놓을 때마다 서버가 판정 |
| 분류 | **puzzle** | 반응속도 완전 비의존 — §7 참조 |
| 한 판 | 오늘 상자의 상품 **6개**를 다 처리하면 종료 | 기획서 6장 (1~2분) |
| 기본 도전 기회 | 하루 **1판** | 기획서 6장 「하루 1판」 |
| 광고 보상 | 보너스 상자 = 도전 기회 +1 (하루 1회) | 기획서 8장 |
| 런 중 이어하기 | **없음** (`boostsPerRun: 0`) | 실패가 없어서 되돌릴 것이 없음 |
| 목숨 | **0 = 실패 없음** | 기획서 6장 「실패: 없음」 |
| 선반 | 코너 3개 × **4칸** | 기획서 6장 「첫 선반은 4칸」 |
| 상품 | **20종** (음료·간식·생활) | 기획서 16장 위험 2 — 1차는 최소 구성 |
| 한 수 제한 | 30초 | 판단 시간이지 반응속도가 아닙니다 |

수치는 전부 `src/lib/config.js` 의 `ARCADE.STORE` 에 있습니다.

### 한 판의 흐름

```
[ready]  내 가게 단계 · 오늘 상자 · ▶ 열기          [광고: 보너스 상자]
[play]   상품 1 → 빈 칸 탭 → 딸깍 → 상품 2 … 6      선반이 차면 완성 연출
[over]   오늘 진열 수 · 완성 선반 · 새 도감          [광고: 전체 순위]
```

실패 화면이 없습니다. 잘못 누른 칸은 알려만 주고 **그 상품을 소모하지도, 판을 끝내지도**
않습니다. 판이 끝나는 길은 오늘 상자를 다 쓰는 것뿐입니다.

## 3. 영속 상태 — 이 게임의 핵심

### 왜 새 테이블이 필요한가

기존 영속 상태 테이블은 `user_progress` 뿐인데 `best_level` `best_score` `play_count`
세 값이 전부입니다. 선반의 칸별 진열 내용·도감·완성 이력을 담을 수 없습니다.
그래서 `store_state` 를 신설합니다 (`migrations/0009_store_state.sql`).

```sql
CREATE TABLE store_state (
  user_id      TEXT PRIMARY KEY,
  shelves_json TEXT NOT NULL,   -- 코너별 "진행 중인 선반" 의 칸 배열
  dex_json     TEXT NOT NULL,   -- 진열해 본 상품 id 목록 (도감)
  done_shelves INTEGER NOT NULL DEFAULT 0,  -- 완성한 선반 수 (성장 단계의 근거)
  placed       INTEGER NOT NULL DEFAULT 0,  -- 누적 진열 칸 수 (순위 지표)
  updated_at   INTEGER NOT NULL
);
```

**진행 중인 선반만 저장합니다.** 완성된 선반은 칸 내용을 보관하지 않고 개수(`done_shelves`)만
셉니다. 완성 선반을 전부 보관하면 오래 한 사용자의 행이 계속 자라 D1 용량에 그대로 얹히는데,
화면에 필요한 것은 "몇 개 완성했는가" 와 "지금 채우는 선반이 어디까지 찼는가" 뿐입니다.

### 읽고 쓰는 시점

⑮ 다들 뭐 골랐을까가 열어 둔 훅 두 개를 그대로 씁니다.

| 훅 | 하는 일 |
|---|---|
| `initSecret(meta, ctx)` | 런 시작에 가게 상태를 **한 번** 읽고 오늘 상자를 배정합니다. 라운드마다 읽으면 왕복이 늘어납니다 |
| `onRunEnd(env, meta, ctx)` | 결과가 저장된 뒤 가게 상태를 한 번 씁니다 |

런 도중의 진열은 세션 `meta` 에만 쌓입니다. 중간에 이탈하면 그 판의 진열은 가게에 반영되지
않는데, 이건 ⑮ 의 표 집계와 같은 선택입니다 — 라운드마다 쓰면 왕복이 하나 더 늘고,
그 비용이 이탈 편향보다 큽니다.

**대신 진행 중인 런 자체는 되살립니다.** 이 게임은 하루 한 판이라, 새로고침 한 번에 판이
날아가면 그날을 통째로 잃습니다(다른 게임은 5판 중 하나를 잃을 뿐입니다). 그래서 화면이
`fresh: false` 로 시작해 열려 있는 런을 그대로 이어받습니다 — 기회를 쓰지 않습니다.
기회가 이미 0일 때도 이어받기를 시도하는데, **기회가 없으면 새 런이 생길 수 없으므로**
안전합니다. 진행 중인 런이 있으면 돌아오고, 없으면 `NO_ATTEMPTS` 로 떨어질 뿐입니다.

## 4. 배치 규칙

- 상품마다 **코너**(음료·간식·생활)가 정해져 있고, 그 코너 선반의 **빈 칸에만** 놓입니다.
- 한 코너 선반은 4칸입니다. 4칸이 다 차면 **완성** — 보너스를 주고, 그 자리에 **새 빈 선반**이
  열립니다. 완성 선반 수가 성장 단계의 근거입니다.
- **첫 상품은 반드시 놓을 자리가 있게 배정합니다** (기획서 0-4 「첫 성공 3초 내」).

> **건너뛰기가 없는 이유.** 선반은 4칸이 차는 **순간** 완성 처리되며 즉시 비워집니다.
> 그래서 저장된 상태에서 코너가 꽉 찬 채로 남는 경우가 원리적으로 없고, 놓을 자리는 항상
> 있습니다. 처음에는 "코너가 꽉 차면 건너뛰기" 를 넣었는데 **도달할 수 없는 코드**였습니다.
> 기획서 6장의 「못 채운 칸은 내일로 이월」은 상품이 아니라 **칸**의 이야기이고,
> 그건 진행 중인 선반이 그대로 저장되는 것으로 이미 성립합니다.
> 종료 화면은 그 미완의 선반을 그대로 알려 줍니다 — 「음료 코너, 1칸 남았어요」(기획서 8장).

> **잘못 누른 칸은 상품을 소모하지 않습니다.** 공통 엔진은 판정이 틀려도 라운드를 올립니다
> (`arcade.js` 의 `meta.round += 1`). 라운드 번호로 상자를 짚으면 칸을 잘못 눌렀을 때 그 상품이
> 그대로 사라져, 「실패가 없는 게임」이라 해 놓고 오히려 벌칙이 됩니다.
> 그래서 상자는 **처리를 마친 개수(cursor)** 로 짚습니다 — ⑯ 딱 맞게 담기가 "시도가 남아
> 있으면 직전 문제를 다시 발급" 한 것과 같은 방식입니다.

> **여러 배치를 허용합니다.** 기획서 4장이 "정답은 하나가 아니라 여러 배치 허용 — 널널한
> 정리" 라고 못박았습니다. 코너만 맞으면 어느 칸이든 됩니다. 자리를 하나로 강제하면
> 정리욕이 아니라 퍼즐이 되고, 그 순간 이 게임의 대상 이용자가 바뀝니다.

### 점수

```
배치 1개      +1
선반 완성     +10
도감 신규 등록 +3
```

순위 지표는 **누적 진열 칸 수**(`placed`)입니다. 이 게임에는 잘하고 못하고가 없어서
한 판의 점수로 순위를 매기면 의미가 없습니다. 대신 "가게를 얼마나 키웠는가" 를 세웁니다 —
기획서 9장의 재방문 장치(성장 단계)와 같은 값입니다.

## 5. 기획서와 다르게 구현한 부분

| 항목 | 기획서 | 구현 | 이유 |
|---|---|---|---|
| 조작 | 드래그해 끼움 | **빈 칸을 탭** | 아케이드 규격이 「탭 1종류」입니다(`docs/arcade-10-games.md`). 이 게임의 핵심은 드래그 제스처가 아니라 정리욕과 딸깍의 손맛이라, 탭으로도 그대로 성립합니다. 접근성도 낫습니다 |
| 보너스 상자 | 별도 광고 트리거 | 표준 `STORE_ATTEMPT`(기회 +1) | 아케이드 3종 트리거(`_ATTEMPT` `_BOOST` `_STATS`)가 자동 파생됩니다. 「보너스 상자 1개」는 결국 "한 판 더" 라서 기회 +1 로 그대로 표현됩니다. 트리거를 새로 만들면 파생 규칙 밖의 예외가 하나 생깁니다 |
| 완성 선반 보관 | 가게에 영구히 남음 | 개수만 보관 | §3 참조 — 칸 내용을 전부 쌓으면 행이 계속 자랍니다. 화면에 필요한 것은 개수입니다 |
| 순위 | 언급 없음 | 누적 진열 수 | 아케이드 공통 구조상 `bucket`·`rank_metric` 이 필요합니다. 한 판 점수 대신 성장을 세워 게임의 뜻과 맞췄습니다 |
| 상품 종류 | 광고주 입점 카탈로그 | 코드 상수 20종 | 1차 최소 구성(기획서 16장 위험 2). 광고주 입점은 이 상수를 DB 로 옮기면 되고, 배치·판정 규칙은 그대로입니다 |
| 이월 | 못 놓은 상품이 내일로 | **미완의 칸**이 내일로 | §4 참조 — 코너가 꽉 찬 상태가 존재하지 않아 "못 놓는 상품" 이 생기지 않습니다. 기획서 6장의 문장도 원래 「못 채운 **칸**」입니다 |

## 6. 어뷰징 방지

### 서버가 막는 것

- **상자 배정은 서버** — 오늘 상자의 상품 6개는 세션 secret 에 암호화 저장됩니다.
  클라이언트가 원하는 상품을 고를 수 없습니다.
- **배치 판정도 서버** — 칸이 비었는지, 코너가 맞는지, 이미 놓은 상품인지 전부 서버가 봅니다.
- **하루 1판** — 기본 기회 1회 + 광고 1회. 기회 소진은 KST 자정에 리셋됩니다.
- **가게 상태 위조 불가** — 진열 결과는 클라이언트가 보낸 값이 아니라 서버가 세션에 쌓은
  `meta` 에서 나옵니다. 클라이언트는 "몇 번 칸을 눌렀는가" 만 보냅니다.
- **중복 반영 차단** — 가게 상태는 `onRunEnd` 에서 한 번만 쓰이고, 결과는
  `results.session_id` UNIQUE 로 중복 제출이 막힙니다.

### 남아 있는 한계 (정직한 기록)

- **이탈한 판의 진열은 반영되지 않습니다.** §3 의 이유대로 런이 끝날 때 한 번에 씁니다.
  다만 런 자체는 새로고침으로 되살아나므로, 실제로 잃는 경우는 "판을 끝내지 않고 하루가
  넘어간" 때뿐입니다.
- **도감이 20종에서 멈춥니다.** 하루 6개씩 받으면 2주쯤에 도감이 완성되고, 그 뒤로는
  수집 동기가 사라집니다. 재방문 장치 두 개 중 하나가 그 시점에 죽습니다 —
  §9 의 광고주 입점 카탈로그가 곧 콘텐츠 공급이어야 하는 이유입니다.
- **순위는 실력이 아니라 누적입니다.** 누적 진열 칸 수라서 오래 한 사람이 위에 있고
  신규 사용자는 상위권에 들 수 없습니다. 다른 게임은 첫 판에도 상위권이 가능합니다.
  이 게임에 "잘함" 이 없어서 생긴 구조적 한계이고, 성장 자체를 세우기로 한 선택의 대가입니다.
- **광고 노출이 적습니다.** 하루 최대 2회(기회 1 + 통계 1)로 다른 게임의 약 1/5입니다
  (기획서 16장 위험 3).
- **자동화의 실익이 거의 없습니다.** 이 게임에는 실력도 속도도 없어서 스크립트가 얻는 것은
  "하루 한 판을 대신 눌러 주는 것" 뿐이고, 그 한 판의 보상은 이미 하루 한도로 묶여 있습니다.
  아케이드 다른 게임과 달리 순위 조작 유인 자체가 약합니다.

## 7. 분류 — 왜 puzzle 인가

허브의 아케이드는 `action`(순발력) · `puzzle`(두뇌) 두 묶음입니다.
기준은 **정답을 알아내야 하는가, 정답은 이미 보이는데 제때 해내야 하는가** 입니다.

이 게임은 **puzzle** 입니다.

- 시간이 점수를 가르는 지점이 한 곳도 없습니다. 한 수 제한 30초는 판단 시간이고,
  기획서 자체가 "반응속도 완전 비의존" 을 대상 고객의 조건으로 적고 있습니다.
- 어디에 놓을지는 화면에 답이 있지 않습니다 — 코너를 보고 고릅니다.
  다만 여러 배치를 허용하므로 난도가 높은 판단은 아닙니다.

> 엄밀히 말하면 이 게임은 두 묶음 어디에도 딱 맞지 않습니다. 순발력이 아닌 것은 분명한데,
> 두뇌 쪽의 다른 게임(암산·경로 탐색)만큼 머리를 쓰지도 않습니다. 분류가 둘뿐이라
> **아닌 쪽을 배제하는 방식**으로 puzzle 에 넣었습니다. 수집·성장형이 몇 종 더 늘어나면
> 세 번째 묶음(`collect`)을 만드는 것이 정직합니다.
