**⑱ 와르르 받기** 는 기획서 `../reward-minigame-research/plans/2026-07-29/PLAN-12_와르르받기.md` 기준입니다.
떨어지는 상품을 바구니로 받고 폭탄만 피합니다. 자사 배포분에 **낙하·받기형이 한 종도 없었습니다** —
지금까지는 전부 멈춰 있는 것을 고르는 게임이었고, 손을 계속 움직이는 게임은 이것이 처음입니다.

> **BATCH 인 이유.** 실시간 낙하 게임에서 물체마다 서버 왕복을 하면 왕복 지연이 그대로
> 조작감을 망칩니다. 그래서 ⑤ 반응속도와 같은 구조입니다 — **낙하 일정을 서버가 미리
> 확정**해 내려주고 화면은 그것을 재생만 하며, 끝나고 결과 전체를 제출하면 서버가 원본
> 일정과 대조해 다시 채점합니다. 점수를 클라이언트가 정할 수 없습니다.

> **조작은 포인터 추종 하나뿐입니다.** 누른 채 움직이면 따라오고 그냥 탭해도 그 자리로
> 갑니다. 아케이드 규격의 「탭 1종류」(docs/arcade-10-games.md)에서 한 걸음 나간 유일한
> 게임인데, 탭만으로도 완전히 플레이되도록 만들어 규격의 의도(WebView 어디서든 동일 동작)는
> 지켰습니다.

**⑰ 한 줄로 이어요** 는 기획서 `../reward-minigame-research/plans/2026-07-28/PLAN-11_한줄로이어요.md` 기준입니다.
번호를 순서대로 지나는 한 줄을 긋되 지나간 칸은 다시 밟을 수 없습니다. 자사 배포분에
**경로·공간 퍼즐이 한 종도 없었습니다** — 지나온 자리가 다음 수를 제약하는 구조는 처음입니다.

> 해가 없는 판을 내지 않으려고 **정답 경로를 먼저 만들고 그 위에 번호를 얹습니다.**
> '최단' 은 생성된 경로 길이가 아니라 **인접 번호 사이 맨해튼 거리의 합**(하한)입니다 —
> 생성 경로는 랜덤 워크라 대개 최단이 아니어서, 그걸 최단이라 부르면 실제로 최단으로
> 푼 사람이 보너스를 못 받습니다.

**⑯ 딱 맞게 담기** 는 기획서 `../reward-minigame-research/plans/2026-07-28/PLAN-09_딱맞게담기.md` 기준입니다.
제시된 금액에 딱 맞게 상품을 담는데, **시간 제한이 없고 시도 3회가 제한**입니다.
이미 있는 ⑨ 60초 암산과 계산 소재가 겹치므로 압박의 원천을 시간에서 시도로 옮겨
빠른 연산이 아니라 조합 탐색을 묻는 게임으로 갈라놓았습니다.
목표 금액은 반드시 실제 상품 조합의 합에서 뽑습니다 — 임의의 숫자를 던지면 해가 없는
판이 나오고 그 순간 실력이 아니라 운이 됩니다.

> 공통 엔진은 판정 후 곧바로 다음 라운드를 냅니다. "같은 문제에 세 번 도전" 을 그대로
> 표현할 수 없어, **한 라운드를 한 번의 시도로 두고** 시도가 남아 있으면 `makeRound` 가
> 직전 문제를 다시 발급하는 방식으로 맞췄습니다.

**⑮ 다들 뭐 골랐을까** 는 기획서 [`docs/majority-game.md`](docs/majority-game.md) 기준입니다.
앞의 14종과 규칙 체계는 같지만 **정답의 출처가 다릅니다** — 서버 난수가 아니라
*다른 사람들이 실제로 고른 결과*입니다. 두 보기 중 다수가 고른 쪽을 3연속 맞히면 완주.
정답이 미리 존재하지 않으므로 정답 아카이브가 성립하기 어렵고, 팽팽한 문항일수록
점수가 높아 쏠린 문항을 외워 오는 것의 실익이 가장 작습니다.

아케이드 14종의 광고 트리거는 게임마다 3종으로 같습니다 —
`{GAME}_ATTEMPT`(기회 +1, 하루 5회) · `{GAME}_BOOST`(런 중 보상, 1런당 2회) ·
`{GAME}_STATS`(전체 순위 열람). 보상을 쓴 런은 bucket 에 `+` 가 붙어 별도 리그로 집계되므로
순위표가 광고 시청량 순위가 되지 않습니다.

### 아케이드 게임을 추가할 때

손댈 파일은 다섯 개뿐입니다. 라우터·광고·통계는 목록에서 자동으로 파생됩니다.

1. `src/lib/config.js` 의 `ARCADE` 에 수치 추가 (ENDLESS 면 `lives` 필수)
2. `src/games/arcade/<게임>.js` 에 spec 작성 (라운드 생성 + 판정만)
3. `src/games/arcade/index.js` 레지스트리에 등록
4. `public/games/<게임>/` 에 index.html + game.js
5. `scripts/test-api.mjs` 의 `PLAYERS` 에 플레이 방법 추가

DB 마이그레이션은 필요 없습니다. `sessions.game_type` 제약이 형식 검사로 되어 있고
허용 목록은 `GAME_TYPES` 한 곳에서만 관리합니다.

> 예외는 ⑮ 다들 뭐 골랐을까입니다. 그 게임의 정답은 서버 난수가 아니라 **사용자들의 선택
> 집계**라서 사용자 간 공용 테이블이 필요합니다(`migrations/0007`, `0008`).
> 그러면서 공통 엔진에 선택 훅 네 개(`initSecret` 의 `await`·`ctx`, `makeRound` 의 세 번째
> 인자, `detailOf`, `onRunEnd`)를 넓혔고, 기존 10종의 코드는 바뀌지 않았습니다.
> 자세한 내용은 [`docs/majority-game.md` §9](docs/majority-game.md) 에 있습니다.

주의할 점과 그 이유는 [`docs/arcade-10-games.md` §9 체크리스트](docs/arcade-10-games.md)에
정리해 두었습니다 (실제로 겪은 버그에서 나온 목록입니다).

## 배포

`main` 브랜치에 push하면 Cloudflare Workers Builds가 자동 배포합니다.
따라서 별도로 `wrangler deploy` 를 실행할 필요가 없습니다. 두 번 하면 push 한 번에
버전이 두 개 생깁니다.

`main` 이 아닌 브랜치는 `wrangler versions upload` 로 미리보기 버전만 만들고 프로덕션에는
영향을 주지 않습니다. (대시보드 Build configuration 의 *Non-production branch deploy command*
가 `npx wrangler deploy` 로 되어 있으면 어떤 브랜치든 프로덕션을 덮어쓰므로 주의)

처음 한 번만 필요한 작업:

```bash
npx wrangler login
npx wrangler d1 create minigames-db          # 출력된 database_id 를 wrangler.jsonc 에 기입
npx wrangler d1 migrations apply minigames-db --remote
npx wrangler secret put SESSION_SECRET        # 운영용 랜덤 값
```

## 문장 DB 수정

문장을 추가·수정할 때는 SQL을 직접 고치지 않고 스크립트를 고칩니다.

```bash
# scripts/gen-sentences.mjs 의 배열을 편집한 뒤
node scripts/gen-sentences.mjs
```

글자수·단어수를 스크립트가 계산하고, 중복 문장과 기획서 최소 수량(한국어 100 / 영어 100 / 혼합 50)을 검증합니다.
현재 수량: **한국어 110 · English 110 · 한·영 혼합 55 = 275문장**

## 문항 은행 수정 (⑮ 다들 뭐 골랐을까)

같은 방식입니다. SQL 을 직접 고치지 않고 스크립트를 고칩니다.

```bash
# scripts/gen-majority-questions.mjs 의 배열을 편집한 뒤
node scripts/gen-majority-questions.mjs
```

질문 길이(24자)·보기 길이(12자)·중복을 스크립트가 검증합니다. 현재 **74문항**.

> **이미 마이그레이션을 적용한 DB 에는 재생성만으로 반영되지 않습니다.** 적용 이력이
> 남아 있어 `0008` 은 내용을 바꿔도 다시 실행되지 않습니다. 운영에 문항을 추가할 때는
> 새 마이그레이션 파일에 추가분만 `INSERT` 하고, 배열에도 함께 넣어 단일 출처를
> 유지합니다. 같은 제약이 아래 문장 DB(`0002`)에도 있습니다.
> 자세한 절차와 중복 확인 방법은 [`docs/majority-game.md` §8](docs/majority-game.md).

## 어뷰징 방지 구조

- **정답 비노출**: 숫자야구 정답은 AES-256-GCM으로 암호화해 D1에 저장하고, 게임이 끝날 때까지 어떤 응답에도 넣지 않습니다. S/B 판정도 서버가 합니다.
- **시간 검증**: 측정은 브라우저 `performance.now()`(단조 증가 시계)로 하고, 서버는 세션 생성 시각과 플레이 시작 시각(`armed_ts`)을 기록해 신고값이 물리적으로 가능한 범위인지 검사합니다. 시간창을 넘으면 `TIME_TAMPERED` 로 거부합니다.
- **중복 제출 차단**: `results.session_id` UNIQUE 제약 + 세션 상태(`OPEN`/`CLOSED`).
- **정확도 재계산**: 타이핑 정확도·점수는 클라이언트 값을 믿지 않고 원본 문장과 제출 문자열을 비교해 서버가 다시 계산합니다.
- **비정상 속도 차단**: 600 WPM 초과는 거부하고 이상치로 기록합니다.
- **광고 한도**: 트리거별 일일/게임당 한도와 동일 IP 일일 20회 제한을 서버가 강제합니다.
- **익명 신원 위조 방지**: `user_id` 쿠키는 HMAC-SHA256 서명이 붙어 임의 값으로 바꿀 수 없습니다.
- **링 스톱 각도 재현**: 클라이언트가 보낸 각도를 판정에 쓰지 않고, 서버가 `시작각 + 각속도 × 경과시간` 으로 직접 계산해 판정합니다. 신고 각도는 재현값과 대조하는 정합성 확인에만 씁니다.
- **카드 배치 비노출**: 카드 짝 맞추기 배치는 서버 세션에만 있고, 뒤집을 때마다 그 자리의 그림 하나만 내려갑니다.
- **집계 비율 비노출(⑮)**: 다수 비율이 곧 정답이므로 문항과 함께 내려보내지 않고, 판정이 끝난 응답에만 넣습니다. 문항 묶음과 그 시점의 집계는 세션에 암호화해 둡니다.
- **표(집계) 오염 차단(⑮)**: 순위보다 먼저 지켜야 하는 것이 비율입니다. ① 표는 그 사용자의 **하루 첫 판**만 셉니다(기획서의 「1일 1세션」을 표 쪽에만 적용) ② 응답 하한 1.5초 미만은 세지 않습니다 ③ 표는 결과가 저장된 뒤 한 번의 batch 로 반영되므로 중복 제출로 두 번 들어가지 않습니다.
- **응답 시간 하한(비율 판정)**: 자동 입력은 거의 모든 문항이 사람 하한보다 빠릅니다. 하한 미만이 네 개를 넘고 동시에 전체의 20% 이상일 때만 이상치로 봅니다. 손이 미끄러진 한두 번으로 판 전체가 순위에서 빠지지 않게 하기 위한 기준입니다.
- **이상치는 개인 최고 기록에도 안 남김**: 이상치 판을 최고 기록으로 두면 정상 플레이로는 깰 수 없는 목표가 되어 재도전 동기가 사라집니다.

### 남아 있는 한계 (정직한 기록)

- **클라이언트 측정의 미세 조작**: 스탑워치는 "실제로 3.5초쯤 기다린 뒤 3.470초라고 신고"하는 조작을 서버가 완전히 구분할 수 없습니다. `armed_ts` 기반 시간창 검증으로 폭을 네트워크 지연 수준까지 좁혔고, 사람이 도달하기 어려운 정확도(오차 2ms 미만)는 이상치로 표시해 통계에서 제외합니다. 완전 차단에는 입력 이벤트 타임라인 전송 후 서버 재현 검증이 필요합니다. 반응속도 테스트(⑤)와 링 스톱(⑪)도 같은 성질의 한계를 갖습니다.
- **기억력 문제 값 노출**: 암기할 숫자는 화면에 보여줘야 하므로 개발자도구로 읽는 것을 막을 수 없습니다. 채점은 서버가 하므로 결과 위조는 불가능합니다. 완전 차단에는 숫자를 서버에서 이미지로 렌더링해야 합니다. 색 다른 타일(⑥)·순서 기억(⑦)·순간 개수 세기(⑫)도 같습니다.
- **⑮ 의 아카이브 유통**: 정답이 미리 존재하지 않으므로 정답 아카이브는 만들 수 없지만, "어제까지의 집계" 는 하루 동안 고정입니다. 비율이 안정된 문항은 그 하루치 정보가 유통될 수 있습니다. 막은 것은 **유효기간**(영구 → 하루)과 **실익**(쏠린 문항일수록 점수가 낮음)이며, 완전 차단이 아닙니다. 문항 무작위 배정·좌우 무작위·은행 확대가 실질 방어입니다. 자세한 내용은 [`docs/majority-game.md` §6](docs/majority-game.md).
- **자명한 문제의 자동화**: 암산(⑨)·스트룹(⑩)·이겨라/져라(⑭)는 문제만 있으면 스크립트가 항상 정답을 냅니다. 응답 시간 하한으로 이상치 처리만 합니다. 광고 보상은 판정 결과가 아니라 광고 시청 여부에 걸려 있고 광고 한도는 서버가 따로 강제하므로, 랭킹 조작의 실익이 광고 수익에 영향을 주지 않습니다.
- **광고 시청 검증**: 광고 플랫폼 SSV 스펙이 없어 현재는 목업 통과입니다. 아래 참조.

## 광고 연동 (미완 — 스펙 대기)

기획서 11장의 트리거·보상·한도는 **서버에서 이미 강제**하고 있고, 화면에도 광고 자리와 보상 흐름이
들어가 있습니다. 실제 광고 SDK 호출과 서버 검증만 비어 있습니다.

연동 시 고칠 파일은 두 개입니다.

| 파일 | 채울 내용 |
|---|---|
| `public/shared/ad.js` | `loadAdSdk()`, `showRewardedAd()`, `showInterstitialAd()` — 목업 오버레이를 SDK 호출로 교체 |
| `src/lib/adverify.js` | `verifyRewardedCallback()`, `verifyInterstitialImpression()` — SSV 서명 검증, transaction_id 재사용 차단 |

함수 시그니처를 유지하면 게임 코드는 수정할 필요가 없습니다.
`AD_MODE=live` 로 바꿨는데 검증 구현이 비어 있으면 조용히 통과하지 않고 `501` 로 실패합니다
(미구현 상태로 실서비스에 나가 보상이 무료 지급되는 것을 막는 안전장치).

게임이 18개로 늘었지만 **연동 작업량은 그대로 두 파일**입니다. 아케이드 13종의 트리거는
접미사 규칙(`_STATS` → Interstitial, 나머지 → Rewarded)으로 처리되므로 목록을 손으로
관리하지 않습니다.

> 참고: Rewarded / Interstitial 은 원래 모바일 앱 SDK 기능이라 순수 웹에서는 그대로 재현되지 않습니다.
> WebView 로 감쌀 때 네이티브 브리지를 통해 호출하는 형태가 됩니다 (기획서 13장 "WebView 우선 개발" 과 동일한 방향).

| 항목 | 기획서 | 구현 | 이유 |

## 테스트

```bash
npm run dev          # 터미널 1
npm run test:api     # 터미널 2
```

`scripts/test-api.mjs` 가 네 부분을 확인합니다.

| 구간 | 내용 |
|---|---|
| ① spec 계약 | 등록된 아케이드 게임의 spec·config 형태를 정적 검증. 필드 누락·mode 불일치·보상 미구현을 잡습니다 |
| ② 아케이드 공통 흐름 | **등록된 게임 전부**에 같은 시나리오 — 시작 → 라운드/제출 → 오답 → 이어하기 → 결과 → 통계 게이팅 |
| ③ 공통 규칙 | 시간 조작 거부, 채점 기준값 비노출, 런당·일일·IP 광고 한도, 새로고침 복구 |
| ④ 오리지널 4종 회귀 | 공용 모듈을 고쳤을 때 기존 게임이 깨지지 않았는지 |

어뷰징 방어는 따로 있습니다.

```bash
npm run test:abuse
```

`scripts/test-abuse.mjs` 는 공격자 입장에서 실제로 뚫어 봅니다 — 남의 세션 사용, 쿠키 위조,
점수·정답 주입, 리플레이·동시 제출 경합, 시간 조작(음수·Infinity·되돌리기), 기회·광고 한도
우회, 통계 게이팅 우회, SQL 주입, 게임별 규칙 악용, 리그 조작. 통과는 "공격이 실패했다" 는
뜻입니다. 실제로 이 테스트가 순위표 1위를 영구 점유할 수 있는 취약점을 잡아냈습니다.

②가 레지스트리를 순회하므로 **게임을 추가하면 자동으로 검사 대상**이 됩니다.
`PLAYERS` 에 플레이 방법을 추가하지 않으면 "테스트 커버리지" 항목이 실패해,
테스트 없이 게임이 들어가는 것을 막습니다.

브라우저 확인도 함께 하세요. API가 통과해도 화면 배선(id 오타, 이벤트 미연결)은
이 테스트가 잡지 못합니다.
